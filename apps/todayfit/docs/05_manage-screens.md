# 05. 관리 화면 설계 (manage screens)

달력 `S-02` · 설정 `S-03` · 관리 화면 여덟(`S-04`~`S-11`)의 구현 설계.

무엇을 왜 그렇게 정했는가는 기획서 `planning-todayfit.html`, 규칙은 `01_spec.md`, 수치는 `02_data.md`, 폴더와 의존성은 `03_architecture.md`가 SSOT다. 이 문서는 그 넷이 정한 것을 **어떤 파일이 어떤 모양으로 만드는가**만 적는다.

이 판의 목표는 화면 개수 채우기가 아니라 **운동 등록 → 루틴 → 요일 규칙 → 월간 계획 생성 → 오늘 화면에 운동 표시가 실제로 한 바퀴 도는 것**이다(사용자 지시 2026-09-18). 걸음 순서(7장)가 그 한 바퀴를 앞에 둔다.

## 1. 이 판이 만드는 것

1.1. 화면 열하나.

| 화면 | 번호 | 자리 | 이 판의 걸음 |
|---|---|---|---|
| 설정 | `S-03` | 주 화면. 관리 화면 진입 통로 | A |
| 운동 템플릿 목록 | `S-09` | 설정 하위 | B |
| 운동 템플릿 편집 | `S-10` | 목록 하위 | B |
| 루틴 목록 | `S-07` | 설정 하위 | C |
| 루틴 편집 | `S-08` | 목록 하위 | C |
| 요일 규칙 | `S-06` | 설정 하위 | D |
| 달력 - 달 이동과 월간 계획 생성 | `S-02` 앞절반 | 주 화면 | E |
| 달력 - 격자와 달성 현황 | `S-02` 뒷절반 | 주 화면 | F |
| 날짜 상세 | `S-04` | 달력 하위 | G |
| 날짜별 계획 수정 | `S-05` | 날짜 상세 하위 | G |
| 기본값과 소리 | `S-11` | 설정 하위 | H |

1.2. 달력 `S-02`를 걸음 둘로 가르는 이유는 **월간 계획 생성이 달력 화면 안에 있기 때문**이다(기획서 5.1). 한 바퀴를 닫으려면 계획 생성 조작이 먼저 서야 하고, 격자와 달성 현황은 그 한 바퀴에 필요하지 않다.

1.3. 이 판이 손대지 않는 것 - 운동 실행 `S-12` · 종료 요약 `S-13` · 오늘 화면 `S-01`. 오늘 화면은 이미 계획을 읽어 그리므로 계획이 생기면 저절로 뜬다. **그 사실이 이 판의 확인 경로다**(7.2).

## 2. 새 파일과 자리

2.1. 새로 만드는 파일.

```
src/
├── manage.js                     관리 화면 묶음의 조립·전환·저장 (main.js 가 부름)
├── core/
│   ├── validate.js               입력 범위 검사 (02_data.md 1.3)
│   └── cascade.js                지움이 번지는 자리 · 참조 세기 (순수 함수)
├── platform/
│   └── id.js                     새 항목의 식별자
└── render/
    ├── parts.js                  화면 공통 조각 (머리 · 목록 행 · 입력 칸 · 버튼)
    ├── settingsView.js           설정 S-03
    ├── exerciseListView.js       운동 템플릿 목록 S-09
    ├── exerciseEditView.js       운동 템플릿 편집 S-10
    ├── routineListView.js        루틴 목록 S-07
    ├── routineEditView.js        루틴 편집 S-08
    ├── weeklyView.js             요일 규칙 S-06
    ├── calendarView.js           달력 S-02
    ├── dayView.js                날짜 상세 S-04
    └── planEditView.js           날짜별 계획 수정 S-05
```

2.2. `03_architecture.md` 1.1이 예정한 `manageView.js` 하나에 화면 일곱을 담지 않고 화면마다 파일을 나눈다. 기존 화면 파일이 60~144줄인데 일곱을 한 파일에 넣으면 600줄이 넘어 고칠 자리를 찾기 어려워진다. `dayView.js`도 날짜 상세와 계획 수정 둘을 겸하기로 되어 있었으나, 하나는 읽기 전용이고 하나는 입력 화면이라 성격이 갈려 `planEditView.js`를 따로 둔다. **이 문서를 반영해 `03_architecture.md` 1.1과 2장을 갱신한다**(`04_conventions.md` 9.1).

2.2.1. **그 대신 `manage.js`가 976줄이 됐다**(2026-09-18 실측). 화면 파일은 49~139줄로 잘게 남았지만, 아홉 화면의 모델 만들기와 저장 처리가 한 파일에 모였다. 화면 쪽에서 피한 큰 파일이 조립 쪽에 생긴 것이고, 이 판에서는 동작에 지장이 없어 그대로 둔다. 다음에 화면이 더 붙으면 화면 묶음별(운동 · 루틴 · 요일과 달력 · 날짜)로 가르는 것을 먼저 본다.

2.3. 고치는 기존 파일.

| 파일 | 무엇을 |
|---|---|
| `src/main.js` | 이동 막대의 달력·설정 자리를 임시 안내에서 실제 화면으로 잇는다. 관리 화면 묶음을 띄우고 닫는다 |
| `src/data/phrases.js` | 이 판의 화면 글자 전부 |
| `src/data/constants.js` | 이 판에 필요한 새 수치(2.5) |
| `styles/main.css` | 관리 화면 공통 모양 + 화면별 자리 |
| `styles/tokens.css` | 달력 격자에 쓰는 값 |
| `tests/runner.js` | 새 suite 둘 등록 |
| `docs/03_architecture.md` | 파일 나무와 의존성 갱신(2.2) |
| `CLAUDE.md` | 문서 인덱스에 이 문서 추가, 현재 상태 갱신 |

2.4. **`src/core/`의 기존 일곱은 고치지 않는다.** 계획 생성(`planner.js`) · 값 사다리(`resolve.js`) · 날짜 상태(`dayStatus.js`) · 집계(`stats.js`) · 예상 시간(`estimate.js`) · 날짜 키(`datekey.js`)는 이미 이 판이 필요한 것을 전부 갖고 있다. 새로 붙는 규칙은 `validate.js`와 `cascade.js` 둘뿐이다.

2.5. 새 수치 (`02_data.md`에 먼저 적고 `constants.js`를 맞춘다).

| 이름 | 상수 | 값 | 쓰는 자리 |
|---|---|---|---|
| 이름 글자 수 상한 | `NAME_MAX_LENGTH` | 20 | 운동명 · 루틴 이름 입력 칸 |
| 새 운동의 처음 값 | `NEW_EXERCISE` | 3세트 · 10회 · 시간 둘은 빈 값 | 새 운동을 만들 때 |

격자 줄 수는 상수로 두지 않는다. 한 달 날짜 수와 첫 요일만큼 칸을 채우면 줄 수가 저절로 나오고, 수치를 따로 두면 그 둘과 어긋날 자리가 생긴다(2026-09-18 검사에서 쓰이지 않는 상수로 적발).

## 3. 화면 전환

3.1. **관리 화면은 계단이다.** 설정에서 목록으로, 목록에서 편집으로 들어가고 뒤로 버튼으로 되돌아온다. 그 계단을 `manage.js`가 배열 하나로 갖는다.

```
stack = [{ name: 'settings' }, { name: 'routineList' }, { name: 'routineEdit', id: 'r1' }]
                                                          ↑ 지금 보이는 화면은 항상 맨 끝
```

3.2. `manage.js`가 내놓는 것.

| 이름 | 하는 일 |
|---|---|
| `open(name, params)` | 계단에 한 칸 쌓고 그린다 |
| `back()` | 한 칸 빼고 그린다. 마지막 칸이면 `onExit` 을 부른다 |
| `reset(name)` | 계단을 비우고 그 화면 하나로 시작한다. 이동 막대로 들어올 때 쓴다 |
| `el` | 지금 화면의 DOM. `main.js` 가 무대에 꽂는다 |

3.3. 뒤로 가기는 **화면 머리 왼쪽 버튼**이다. 브라우저 뒤로 가기는 실행 화면 둘에만 걸어 두었고(`main.js`의 이력 칸), 관리 화면에는 걸지 않는다 - 계단 깊이만큼 이력 칸을 쌓으면 실행 화면의 막기 규칙과 얽힌다. 상단 띠의 홈 링크는 그대로 둔다.

3.4. 이동 막대(`오늘` · `달력` · `설정`)는 관리 화면에서도 보인다. 다른 자리를 누르면 계단을 버리고 그 주 화면으로 간다. 편집 도중 이동 막대를 눌러도 확인 창을 띄우지 않는다 - 3.5의 즉시 저장 때문에 잃을 값이 없다.

3.5. **입력은 고치는 즉시 저장한다.** 저장 버튼을 따로 두지 않는다.

- 이 앱은 혼자 쓰는 앱이고 저장 대상이 작다(운동 템플릿 열 몇 개, 루틴 두셋)
- 저장 버튼을 두면 "저장을 안 누르고 나갔다"가 유일하고 잦은 사고가 된다
- 값이 사다리를 타고 아래로 흐르므로(`01_spec.md` 3.2) 즉시 반영이 오히려 규칙과 맞는다
- 예외는 **되돌릴 수 없는 조작 셋**이다 - 루틴 삭제 · 운동 템플릿 삭제 · 날짜 계획 삭제. 이 셋만 확인 창을 띄운다(기획서 5.2)

3.6. 글자 입력 칸은 `change`(칸을 떠날 때)에 저장하고, 켜고 끄는 자리와 고르는 자리는 `input`·`click` 즉시 저장한다. 글자를 한 자 칠 때마다 저장하면 저장 장치를 계속 두드린다.

3.6.1. **입력 칸에서 온 저장은 화면을 다시 그리지 않는다.** 바뀌는 자리(예상 시간 · 값의 출처 표기 · 접힌 줄 요약)만 고쳐 쓴다.

- 다시 그리면 사용자가 지금 누르려던 다음 칸이 그 사이에 DOM 에서 떨어져 나가, 그 한 번이 헛눌림이 된다. 값 넷을 이어 고칠 때마다 걸린다(2026-09-18 검사 적발 - `change`가 브라우저의 click 전달보다 먼저 온다)
- 그래서 편집 화면 둘은 `update`(전체) 말고 `patch`(바뀐 자리만)를 함께 내놓는다
- 버튼 조작(항목 추가·삭제·순서 이동·토글)은 그대로 전체를 다시 그린다. 누른 뒤 다른 곳을 곧바로 누르는 흐름이 아니라서 같은 문제가 없다

## 4. 화면별 설계

각 화면 파일은 기존 화면과 같은 모양을 따른다 - `createXxxView(handlers)` 가 `{ el, update(model) }` 를 돌려주고, **상태를 바꾸지 않고 콜백으로 바깥에 알린다**(`03_architecture.md` 2.3). 저장은 전부 `manage.js`가 한다.

### 4.1. 설정 `S-03` - `settingsView.js`

4.1.1. 표시 - 관리 화면 넷으로 가는 줄. 각 줄은 이름과 지금 상태를 함께 보인다.

| 줄 | 곁들이는 값 |
|---|---|
| 운동 템플릿 | 등록한 개수 |
| 루틴 | 등록한 개수 |
| 요일 규칙 | 쓰는 요일 (`월 · 수 · 금`), 없으면 안내 |
| 기본값과 소리 | 준비·휴식 두 값 요약 |

4.1.2. 이 화면에는 뒤로 버튼이 없다. 이동 막대에서 바로 들어오는 주 화면이다.

4.1.3. **비어 있을 때가 첫 화면이다.** 아무것도 등록하지 않은 상태에서 이 화면이 앱의 출발점이 되므로, 맨 위에 무엇부터 하면 되는지 한 줄을 둔다(운동 템플릿부터 만들면 된다는 안내). 하나라도 등록되면 그 줄은 사라진다.

### 4.2. 운동 템플릿 목록 `S-09` - `exerciseListView.js`

4.2.1. 표시 (기획서 4.7) - 운동명 · 기본 세트 수 × 기본 반복 횟수 · 참조하는 루틴 수.

4.2.2. 조작 - 줄 선택(편집으로) · 새 운동 · 삭제.

4.2.3. 새 운동은 **빈 템플릿을 만들고 바로 편집으로 들어간다**(기획서 5.1). 이름 없는 템플릿이 저장에 남으므로, 편집 화면에서 이름을 비운 채 나가면 그 템플릿을 지운다(4.3.4).

4.2.4. 삭제는 확인 창을 거친다. 참조하는 루틴이 있으면 확인 창 본문에 그 수를 적고, 확인 시 `cascade.js`가 그 루틴들의 해당 항목을 함께 지운다(5.2).

4.2.5. 목록이 비면 안내 한 줄과 새 운동 버튼만 보인다.

### 4.3. 운동 템플릿 편집 `S-10` - `exerciseEditView.js`

4.3.1. 입력 다섯 (기획서 4.7, `02_data.md` 5.1).

| 칸 | 형 | 비울 수 |
|---|---|---|
| 운동명 | 글자 | 불가 |
| 기본 세트 수 | 수 | 불가 |
| 기본 반복 횟수 | 수 | 불가 |
| 기본 세트당 권장 수행시간 | 수 | **가능** - 비우면 앱 기본값 |
| 기본 세트 간 휴식시간 | 수 | **가능** - 비우면 앱 기본값 |

4.3.2. 시간 두 칸은 비울 수 있고, 비었을 때 **지금 앱 기본값이 얼마인지를 칸 아래 안내로 보인다**. 값 사다리(`01_spec.md` 3.5)를 화면에서 읽을 수 있게 하는 자리다.

4.3.3. 범위 밖 값은 저장하지 않고 칸에서 막는다(`02_data.md` 1.3). `validate.js`가 판정하고, 막힌 칸은 아래에 허용 범위를 글자로 보인다.

4.3.4. **이름을 비운 채 나가는 경우를 둘로 가른다**(사용자 결정 2026-09-18).

| 경우 | 처리 |
|---|---|
| 새 운동을 눌러 만든 빈 템플릿에 이름을 넣지 않고 나감 | 그 임시 항목을 버린다 |
| 이미 있던 운동의 이름을 비움 | **저장하지 않고 이전 이름을 그대로 둔다.** 칸 아래에 이름이 비었다는 오류를 보인다 |

- 이름을 비우는 것으로 운동이 지워지면, 이름을 고치려다 실수로 지운 사용자가 **다른 루틴이 참조하던 운동까지 함께 잃는다**. 지움은 지움 조작으로만 일어나야 한다
- 따라서 이미 있던 운동을 없애는 길은 목록의 삭제 조작 + 확인 창 하나뿐이다(4.2.4)
- 새 템플릿인지 이미 있던 것인지는 `manage.js`가 편집 화면을 열 때 표시해 준다. 화면이 스스로 판정하지 않는다

4.3.5. 저장하면 참조 루틴에 즉시 반영되고 **이미 생성된 날짜별 계획에는 영향이 없다**(기획서 5.1). 이 규칙은 코드가 지키는 것이 아니라 값 복사(`01_spec.md` 3.3)가 이미 지키고 있다. 화면에 그 사실을 한 줄로 적는다.

### 4.4. 루틴 목록 `S-07` - `routineListView.js`

4.4.1. 표시 (기획서 4.6) - 루틴 이름 · 운동 수 · 예상 소요시간 · 연결된 요일.

4.4.2. 예상 소요시간은 `resolve.expandRoutine`으로 값을 편 뒤 `estimate.estimatePlanSeconds`에 넣어 구한다. 날짜별 계획이 아직 없어도 루틴만으로 잴 수 있다.

4.4.3. 조작 - 줄 선택(편집으로) · 새 루틴 · 복제 · 삭제.

4.4.3.1. 새 루틴도 운동 템플릿과 같이 **빈 것을 만들고 바로 편집으로 들어간다.** 이름을 그대로 두고 운동도 담지 않은 채 나가면 그 루틴을 버린다 - 그러지 않으면 목록에 `새 루틴 · 0개 · 0분`이 영영 남고, 그것을 요일에 걸면 계획이 만들어지지 않는 요일이 된다(2026-09-18 검사 적발).

4.4.4. 복제는 같은 구성의 루틴을 만들고 이름 뒤에 사본 표시를 붙인다. 항목 배열은 **깊은 사본**이어야 한다 - 얕게 복사하면 한쪽 루틴의 덮어쓰기 값이 다른 쪽에 같이 바뀐다.

4.4.5. 삭제는 확인 창을 거치고, 그 루틴을 쓰는 요일이 있으면 확인 창에 적은 뒤 그 요일의 연결을 푼다(`cascade.js`, 5.2).

### 4.5. 루틴 편집 `S-08` - `routineEditView.js`

4.5.1. 표시 (기획서 4.6) - 루틴 이름 · 운동 항목 순서 목록 · 네 값의 출처 표기 · 예상 소요시간.

4.5.2. 항목 한 줄에 드는 것 - 순서 번호 · 운동명 · `세트 수 × 반복 횟수` · 권장 수행시간 · 휴식시간 · 위아래 이동 · 삭제.

4.5.3. **네 값의 출처를 색이 아니라 글자로 보인다**(`04_conventions.md` 5.3). `resolve.sourceOfItem`이 돌려주는 셋을 그대로 쓴다.

| 출처 | 표기 |
|---|---|
| `routine` | 이 루틴에서 지정 |
| `exercise` | 운동 기본값 |
| `settings` | 앱 기본값 |

4.5.4. 항목을 펼치면 덮어쓰기 칸 넷이 나온다. **비우면 덮어쓰기 해제**이고 그 즉시 출처 표기가 아래 단으로 내려간다. 운동명은 덮어쓰기 대상이 아니다(기획서 11.2 열 번째).

4.5.5. 운동 추가는 등록된 운동 템플릿을 고르는 창을 띄우고, 고르면 목록 끝에 덮어쓰기 없는 항목으로 붙인다. 템플릿이 하나도 없으면 고를 것이 없다는 안내를 내고 운동 템플릿 목록으로 가는 줄을 함께 둔다.

4.5.6. 순서 이동은 위·아래 버튼 한 쌍이다. 끌어 옮기기는 두지 않는다 - 목록이 길지 않고, 끌기는 이 앱에 아직 쓰인 적이 없어 손대는 자리가 늘어난다.

4.5.7. 같은 운동 템플릿을 한 루틴에 두 번 넣을 수 있다. 항목마다 덮어쓰기가 따로 서므로 `벤치프레스 무겁게 3세트` + `벤치프레스 가볍게 2세트` 같은 구성이 가능하다.

### 4.6. 요일 규칙 `S-06` - `weeklyView.js`

4.6.1. 표시 (기획서 4.5) - 일곱 줄. 각 줄에 요일 이름 · 사용 여부 · 예정 시간 · 연결 루틴.

4.6.2. 사용 여부를 끄면 그 줄의 시간과 루틴 칸을 흐리게 두되 값은 지우지 않는다. 다시 켤 때 그대로 돌아온다.

4.6.3. 예정 시간은 `"HH:MM"`이다(`02_data.md` 5.3). 브라우저 시간 입력 칸을 쓴다.

4.6.4. 연결 루틴은 등록된 루틴 가운데 고른다. 루틴이 없으면 그 자리에 안내를 내고 루틴 목록으로 가는 줄을 둔다.

4.6.5. **이 화면 아래에 반영 시점 안내를 고정으로 둔다** - 여기서 바꾼 것은 이후 새로 만드는 월간 계획부터 적용되고 이미 만든 계획은 그대로다(기획서 4.5). 값을 복사해 참조를 끊는 구조(`01_spec.md` 3.3)를 사용자가 알 수 있는 유일한 자리다.

4.6.6. 켠 요일이 계획을 만들지 못하는 경우를 그 줄에서 경고한다. 갈래는 둘이다.

| 경우 | 경고 |
|---|---|
| 루틴을 안 걸었다 | 루틴을 골라야 이 요일 계획이 만들어진다 |
| 건 루틴에 담은 운동이 없다 | 그 루틴이 비어 이 요일 계획이 만들어지지 않는다 |

둘째는 **운동 템플릿을 지우면 저절로 생긴다** - 지움이 루틴 항목까지 번져 루틴이 비기 때문이다(5.2). 그 상태에서 요일 화면이 멀쩡해 보이면 사용자는 달력에서 "만들 계획이 없습니다"를 볼 때까지 이유를 모른다(2026-09-18 검사 적발).

### 4.7. 달력 `S-02` - `calendarView.js`

4.7.1. 걸음 E(앞절반)가 만드는 것.

- 연월 표기와 이전·다음 달 이동
- 월간 계획 생성 조작과 미리보기
- 이 달에 계획이 몇 일 있는지 한 줄

4.7.1.1. **이동 막대로 달력을 새로 열면 이번 달부터 본다.** 날짜 상세에 들렀다 뒤로 오는 길에서는 보던 달이 그대로 남는다 - 그 왕복에서 이번 달로 튀면 앞날을 훑던 흐름이 끊긴다(2026-09-18 검사 적발).

4.7.2. 걸음 F(뒷절반)가 얹는 것.

- 달력 격자 (월요일 시작 7열 × 최대 6줄)
- 날짜 상태 표시 넷 - 예정 · 완료 · 부분 완료 · 미실시. **색과 모양을 함께 쓴다**(`02_data.md` 7.3 / 7.4)
- 진행 중 세션이 귀속된 날짜에 진행 중 표기
- 달성 현황 - 이번 주 달성률·진행, 이번 달 달성률·진행, 이번 달 부분 완료 일수
- 날짜를 누르면 날짜 상세로

4.7.3. 상태는 `dayStatus.dayStatusMap`이, 집계는 `stats.weekStats`·`stats.monthStats`가 낸다. 둘 다 이미 있고 테스트도 있다.

4.7.4. 달성률이 없는 기간(도래 계획 0일)은 해당 없음을 글자로 적는다(`01_spec.md` 6.7). 0퍼센트로 적지 않는다 - 하지 않은 것과 할 것이 아직 없는 것은 다르다.

4.7.5. **월간 계획 생성 절차** (`01_spec.md` 3.7).

1. 보고 있는 달과 지금 저장된 요일 규칙·루틴·운동 템플릿·앱 설정으로 `planner.buildMonthPlans`를 부른다
2. 결과를 `planner.previewMonthPlans`로 줄여 미리보기 판에 보인다 - 만들 날짜 수, 날짜별 날짜·요일·시간·루틴 이름·운동 수
3. 확정을 누르면 `repo.putPlans`로 한 번에 저장하고 달력을 다시 그린다
4. 만들 것이 0일이면 확정 버튼 대신 왜 0일인지를 적는다 - 켠 요일이 없는지, 켠 요일에 루틴이 없는지, 그 루틴이 비었는지

4.7.6. 미리보기는 화면을 새로 쌓지 않고 달력 화면 위에 덮는 판으로 낸다. 화면 번호가 붙은 자리가 아니기 때문이다(기획서 5.1은 달력의 조작으로 적었다).

4.7.6.1. **지난 날짜에도 계획이 만들어진다 - 사양대로이며 사용자 결정 대기다.** `01_spec.md` 3.7이 "그 달에서 해당 요일에 드는 날짜를 전부 뽑는다"이므로 달 중간에 처음 만들면 이미 지난 날짜에도 계획이 생기고, 그 날짜들은 곧바로 미실시가 된다.

- 2026-09-18 실측 - 9월 18일에 이번 달 계획을 만들었더니 9월 1일부터 17일까지 열한 날이 미실시로 찍히고 이번 달 달성률이 0퍼센트로 시작했다
- 구현은 사양을 그대로 따랐고 고치지 않았다. 지난 날짜를 건너뛸지는 기획을 바꾸는 일이라 사용자 결정으로 올린다
- 고친다면 `planner.js`의 `buildMonthPlans`에 오늘 이후만 뽑는 갈래를 더하는 쪽이고, 그때 `01_spec.md` 3.7을 먼저 고친다

4.7.7. **이미 만든 계획은 덮어쓰지 않는다**(사용자 결정 2026-09-18). 그 결정을 지키는 자리는 생성 조작을 감추는 것이 아니라 **이미 있는 날짜를 건너뛰는 것**이다(`planner.buildMonthPlans`의 `existingDates`).

- 저장에는 **자동으로 만들어진 계획인지 사용자가 손으로 고친 계획인지 가르는 표식이 없다**(`02_data.md` 5.4). 그래서 있는 날짜는 손대지 않고 빈 날짜만 채운다
- 요일 규칙·루틴·운동 템플릿을 고친 것은 이미 만든 날짜에 닿지 않는다. 그 날짜를 바꾸려면 날짜별 계획 수정으로 하나씩 고친다
- **만들기 조작은 늘 열어 둔다**(2026-09-18 검사 적발 후 고침). 처음에는 "그 달에 계획이 하나라도 있으면 감춘다"로 만들었는데, 4.8.4로 빈 날짜에 하루를 손수 넣는 순간 그 달 나머지를 만들 길이 사라져 막다른 골목이 됐다. 사용자 결정이 막으려던 것은 덮어쓰기이지 생성 자체가 아니다
- 만들 것이 0일이면 왜 0일인지 적는다. 이미 다 만들어진 달이 그중 가장 흔한 경우다

### 4.8. 날짜 상세 `S-04` - `dayView.js`

4.8.1. 읽기 전용 화면이다. 상태에 따라 보이는 것이 갈린다(기획서 4.3).

| 상태 | 보이는 것 |
|---|---|
| 예정 | 날짜 · 예정 시간 · 루틴 이름 · 예정 운동 목록 · 예상 총 운동시간 |
| 완료 · 부분 완료 | 날짜 · 예정 시간 · 전체 상태 · 운동별 결과 · 시작 시각 · 종료 시각 · 총 운동시간 |
| 미실시 | 날짜 · 예정 시간 · 예정이었던 운동 목록 · 미실시 표기 |
| 계획 없음 | 계획 없음 표기 |

4.8.2. 계획 수정으로 가는 줄은 `dayStatus.canEditPlan`이 참일 때만 낸다 - 오늘 이후이고 수행 기록이 없고 지금 운동 중이 아닌 날짜다(`01_spec.md` 3.9 / 3.9.1). 거짓이면 왜 잠겼는지 한 줄로 적는다.

**잠금 갈래가 셋이므로 사유도 셋이다** - 지난 날짜 / 운동한 날짜 / 지금 운동 중인 날짜. 둘만 두면 운동 중인 오늘에 "지난 날짜는 고칠 수 없습니다"가 떠 사용자에게 틀린 사실을 말한다(2026-09-18 검사 적발).

4.8.3. **이 화면에서는 운동을 시작하지 않는다**(`01_spec.md` 2.5). 실행 진입점은 오늘 화면 하나다.

4.8.4. **계획 없는 날짜에는 계획을 새로 만들 수 있다**(사용자 결정 2026-09-18). 월간 기본 일정 밖에 하루를 더 넣는 길이다.

- 계획 없는 날짜이고 오늘 이후이면 `운동 계획 추가` 줄을 낸다. 지난 날짜에는 내지 않는다
- 누르면 날짜별 계획 수정 `S-05`가 **빈 목록으로** 열린다. 거기서 루틴을 불러오거나 운동을 하나씩 담는다
- 운동을 하나도 담지 않고 나가면 그 날짜에 계획이 생기지 않는다(4.9.7)
- 예정 시간의 처음 값은 그 요일의 요일 규칙 시간을 쓰고, 그 요일을 쓰지 않으면 비운다

### 4.9. 날짜별 계획 수정 `S-05` - `planEditView.js`

4.9.1. 입력 (기획서 4.4) - 예정 시간 · 운동 목록(순서 · 운동명 · 세트 수 · 반복 횟수 · 권장 수행시간 · 휴식시간) · 예상 총 운동시간.

4.9.2. **네 수치는 전부 확정값이라 빈 칸이 없다**(`01_spec.md` 3.3). 루틴 편집과 달리 출처 표기가 없고 비울 수도 없다. 이 차이가 두 화면을 한 파일에 담지 않는 이유다.

4.9.3. 예상 총 운동시간은 값을 고칠 때마다 다시 센다(`estimate.estimatePlanSeconds`).

4.9.4. 조작 - 운동 추가(템플릿 고르기) · 삭제 · 순서 이동 · 값 변경 · 루틴에서 불러오기 · 이 날짜 계획 삭제.

4.9.5. 루틴에서 불러오기는 고른 루틴을 `resolve.expandRoutine`으로 편 결과로 **운동 목록을 통째로 갈아 끼운다**. 지금 목록에 붙이지 않는다. 확인 창을 거친다 - 지금 목록이 사라지기 때문이다.

4.9.5.1. **담은 운동이 없는 루틴을 고르면 아무것도 하지 않고 알린다**(2026-09-18 검사 적발). 빈 루틴을 그대로 받으면 목록이 0개가 되고 4.9.7이 그 날짜 계획을 통째로 지운다 - 사용자는 목록을 바꾸겠다고 했지 계획을 지우겠다고 하지 않았다. 계획 삭제는 전용 확인 창을 거치는 조작이다(4.9.6).

**이 판정은 확인 창보다 먼저 선다.** 빈 루틴인지는 고른 순간 이미 알 수 있으므로, 뒤에 두면 "지금 담긴 운동이 사라집니다"에 동의를 받아 놓고 아무 일도 하지 않는 헛걸음이 된다(2026-09-18 재검사 적발).

4.9.6. 계획 삭제는 그 날짜를 계획 없음으로 만든다(`repo.removePlan`). 확인 창을 거치고, 그 날짜가 미실시 집계에서도 빠진다는 것을 본문에 적는다(`01_spec.md` 3.10).

4.9.6.1. **담을 새 운동이 없는 것과 이미 담긴 것이 없는 것은 다르다.** 운동 템플릿을 전부 지운 뒤 이 화면을 열어도 그 날짜에 담긴 운동 목록은 그대로 보인다 - 담을 새 운동이 없다는 안내는 그 위에 따로 붙는다(2026-09-18 검사 적발).

4.9.7. **날짜별 계획은 운동을 적어도 하나 갖는다**(사용자 결정 2026-09-18). 운동 0개인 계획을 저장하지 않는다.

- 0개를 허용하면 계획일로는 세어지는데 시작할 것이 없고 완료할 길도 없는 날짜가 생긴다. 그 날짜가 달성률 분모에 들어가 영원히 미실시로 남는다
- 마지막 하나 남은 운동을 지우려 하면 **삭제 대신 "이 날짜 계획을 지울까요"를 묻는다**(4.9.6과 같은 확인 창으로 이어진다). 확인하면 그 날짜가 계획 없음이 되고, 그만두면 운동이 그대로 남는다
- 계획을 새로 만드는 자리(4.8.4)에서도 같다. 운동을 하나도 담지 않고 나가면 그 날짜에 계획이 생기지 않는다
- 월간 계획 생성도 이미 같은 규칙을 지킨다 - `planner.js`가 빈 루틴의 날짜를 만들지 않는다

### 4.10. 기본값과 소리 `S-11` - `prefsView.js`

4.10.1. 입력 여섯 (`02_data.md` 1장) - 시작 전 준비시간 · 세트당 권장 수행시간 기본값 · 세트 간 휴식시간 기본값 · 운동 간 전환시간 · 음성 안내 · 비프음.

4.10.2. **반영 시점이 둘로 갈리므로 화면에서도 두 묶음으로 가른다**(기획서 4.8).

| 묶음 | 항목 | 반영 |
|---|---|---|
| 새 계획부터 | 권장 수행시간 기본값 · 휴식시간 기본값 | 다음에 만드는 월간 계획부터. 이미 만든 계획은 그대로 |
| 다음 운동부터 | 준비시간 · 전환시간 · 음성 · 비프 | 다음 운동 실행부터 즉시 |

4.10.3. 각 묶음 아래에 그 문장을 그대로 적는다. 항목별로 반복하지 않는다.

4.10.4. 음성 안내 항목은 **기기에 한국어 음성이 없으면 쓸 수 없음을 표시한다**(`03_architecture.md` 4.5.3). 이 화면이 그 표시가 갈 자리로 예정되어 있었다. `platform/speech.js`가 그 판정을 내놓아야 하며, 지금 내놓지 않으면 이 판에서 더한다.

4.10.5. 값을 바꾸면 `main.js`가 들고 있는 `state.settings`도 함께 갱신한다. 저장만 고치면 앱을 다시 열기 전까지 오늘 화면의 예상 시간이 옛 값으로 남는다.

## 5. 새 규칙 모듈

### 5.1. `core/validate.js`

5.1.1. `02_data.md` 1.3의 허용 범위를 판정한다. `LIMITS`를 읽어 정수 여부와 상하한을 본다. 판정 대상이 수·이름·시간 셋으로 갈려 함수도 셋이다.

```
checkNumber(field, raw, allowNull) → { ok, value, min, max, reason }
checkName(raw)                     → { ok, value, max, reason }
checkTime(raw)                     → { ok, value, reason }
```

`reason`은 `blank` · `nan` · `range` · `long` · `format` 가운데 하나다. 화면에 낼 말은 부르는 쪽이 고른다 - 같은 `range`라도 자리마다 문장이 다르다.

5.1.2. 빈 값을 허용하는 칸(운동 템플릿의 시간 둘)은 빈 값을 `null`로 돌려주고 `ok`를 참으로 둔다. 칸마다 빈 값 허용 여부를 인자로 받는다.

5.1.3. 이름 검사는 앞뒤 공백을 떼고 길이가 0인지, `NAME_MAX_LENGTH`를 넘는지만 본다.

### 5.2. `core/cascade.js`

5.2.1. 지움이 번지는 자리 둘과 목록 화면이 보여 줄 참조 수 둘, 그리고 순서 옮기기 하나를 한 파일에 둔다. 다섯 다 순수 함수라 테스트로 덮는다.

| 함수 | 하는 일 |
|---|---|
| `routinesUsingExercise(routines, exerciseId)` | 그 운동을 쓰는 루틴 목록 |
| `weekdaysUsingRoutine(weeklyRules, routineId)` | 그 루틴을 쓰는 요일 번호 목록 |
| `removeExerciseFromRoutines(routines, exerciseId)` | 그 운동 항목을 뺀 새 루틴 목록 |
| `unlinkRoutineFromWeekly(weeklyRules, routineId)` | 그 루틴 연결을 푼 새 요일 규칙. 사용 여부는 건드리지 않는다 |
| `moveItem(list, index, delta)` | 항목 하나를 앞뒤로 옮긴 새 배열. 끝에서 더 가려 하면 그대로 |

`moveItem`은 설계에 없던 다섯째다. 루틴 편집과 계획 수정이 같은 순서 옮기기를 쓰게 되어 여기 모았다(2026-09-18 추가).

5.2.2. 다섯 다 **새 배열을 돌려주고 받은 것을 고치지 않는다**. 저장은 `manage.js`가 한다.

5.2.3. 지운 뒤 빈 루틴이 되어도 그 루틴을 지우지 않는다. 비어 있는 루틴은 월간 계획 생성에서 건너뛰어지므로(`planner.js`) 해가 없고, 사용자가 다시 채울 수 있다.

### 5.3. `platform/id.js`

5.3.1. `crypto.randomUUID()`를 감싼다. 없는 환경에서는 시각과 난수를 이어 붙인 값으로 대신한다.

5.3.2. `core/`가 아니라 `platform/`에 두는 이유는 난수와 시각이 순수 함수가 아니기 때문이다(`03_architecture.md` 2.1).

## 6. 기획 결정 넷 - 확정 (사용자 결정 2026-09-18)

기획서 11.1이 "그 화면을 만드는 시점에 확정한다"고 남긴 일곱 가운데 이번 판에 걸리는 넷이다. 아래가 확정값이며 **기획서 11.1을 이 내용으로 갱신한다**. 나머지 셋(긴 일시정지 제한 · 진행 중 세션 유효 기간 · 데이터 내보내기)은 이 판의 화면과 무관해 건드리지 않는다.

| 번호 | 정한 것 | 확정 | 적는 자리 |
|---|---|---|---|
| 1 | 계획 없는 날짜에 직접 계획 추가 | **둔다.** 날짜 상세에서 계획 추가 → 계획 수정 화면이 빈 목록으로 열린다. 루틴을 불러오거나 운동을 직접 담는다 | 4.8.4 |
| 2 | 다음 달 계획 생성 시점 | **사용자가 달력에서 직접.** 자동 생성하지 않는다 | 4.7.5 |
| 3 | 이미 만든 계획의 취급 | **덮어쓰지 않는다.** 생성은 이미 있는 날짜를 건너뛰고 빈 날짜만 채운다. 만든 계획을 고칠 일은 날짜별 계획 수정으로 한다 | 4.7.7 |
| 6 | 과거 기록 손 수정 | **두지 않는다.** 지난 기록은 읽기 전용이다 | 4.8.1 |

6.1. 3번이 애초 자비스 추천(기록 없는 앞날만 다시 만들기)을 뒤집은 이유를 남긴다 - **저장에 자동 생성분과 손으로 고친 계획을 가르는 표식이 없다.** 그 구별 없이 있는 날짜를 다시 만들면 사용자가 공들여 고친 계획이 조용히 덮인다. 일괄 다시 만들기가 필요해지면 그 표식을 먼저 설계한다.

6.1.1. **그 결정을 지키는 자리는 이미 있는 날짜를 건너뛰는 것이지 생성 조작을 감추는 것이 아니다.** 처음에는 "그 달에 계획이 하나라도 있으면 만들기를 감춘다"로 구현했는데, 1번으로 빈 날짜에 하루를 손수 넣는 순간 그 달 나머지를 만들 길이 사라져 막다른 골목이 됐다(2026-09-18 검사 적발). 결정 하나를 지키려다 같은 사람이 확정한 다른 결정을 막은 것이라, 기획서 11.1 3번의 문면도 "재생성 금지"에서 "덮어쓰기 금지"로 함께 고쳤다.

6.2. 4번 때문에 과거 날짜의 화면은 전부 읽기 전용이다. 날짜 상세에 고치는 줄을 내지 않고, 계획 수정 화면은 애초에 열리지 않는다(`dayStatus.canEditPlan`).

## 8. 하지 말 것

8.1. `src/core/`의 기존 일곱을 고치지 않는다. 계획 생성·값 사다리·날짜 상태·집계·예상 시간이 이미 이 판이 쓸 것을 전부 갖고 있다. 고쳐야 할 것 같으면 그 판단을 먼저 알린다.

8.2. 저장 구조(`02_data.md` 5장)를 바꾸지 않는다. 필드를 더해야 할 것 같으면 멈추고 알린다 - 판 번호 올림과 올림 처리가 따라붙는 일이다.

8.3. 6장 확정을 넘지 않는다. **이미 있는 날짜를 덮어쓰는 일괄 다시 만들기**와 과거 기록 손 수정은 이 판에서 만들지 않는다(빈 날짜만 채우는 생성은 6.1.1대로 열려 있다).

8.4. 화면 글자를 코드에 직접 적지 않는다. 전부 `phrases.js`다(`04_conventions.md` 1.2).

8.5. 숫자를 코드에 직접 적지 않는다. 전부 `constants.js`다(`04_conventions.md` 2.1).

- **예외는 SVG 도형의 좌표다**(`parts.js`의 뒤로 화살표). `viewBox`와 경로 좌표는 조절하는 값이 아니라 그 그림의 정의라서, 상수로 빼면 이름만 늘고 그림은 여전히 그 파일에서만 읽힌다. 아이콘이 여럿 생기면 그때 아이콘 파일로 모은다(2026-09-18 확정)

8.6. 색·간격·글자 크기에 인라인 값을 쓰지 않는다. 토큰 변수만 쓴다(`04_conventions.md` 5.1).

8.7. `localStorage`를 직접 부르지 않는다. `store/repo.js`만 저장에 손댄다(`04_conventions.md` 4.1).

8.8. 공용 자산(`shared/`)을 고치지 않는다. 이 판에서 손댈 공용 파일은 없다.

8.9. 운동 실행 `S-12`와 종료 요약 `S-13`을 건드리지 않는다. 이 판의 범위 밖이다.

8.10. 끌어 옮기기·긴 애니메이션·새 라이브러리를 들이지 않는다.
