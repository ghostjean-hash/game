# 03. 구조 (architecture)

폴더·모듈 구조와 의존성 방향, 그리고 기획서가 `설계 시 검토`로 남긴 여섯 건의 결론.

무엇이 어디에 있고 무엇이 무엇을 부를 수 있는지만 적는다. 규칙은 `01_spec.md`, 수치는 `02_data.md`가 SSOT다.

## 2. 의존성 방향

한 방향으로만 흐른다. 화살표를 거스르는 import는 금지다.

```
main.js ──> core/     ──> data/
   │
   ├─────> store/     ──> data/
   ├─────> render/    ──> data/
   │          └──────> input/          (운동 실행 화면의 다음 버튼 하나, 2.6)
   ├─────> input/     ──> data/
   ├─────> platform/  ──> data/
   │
   └─────> shared/storage, shared/ui, shared/frame/audio (공용 자산)
```

2.1. `core/`는 `document` · `window` · DOM · localStorage를 일체 부르지 않는다. 순수 함수와 상태 객체만이며, 그래서 브라우저 없이 테스트한다.

2.2. `core/session.js`는 시각을 스스로 읽지 않는다. 지금 시각을 인자로 받는다. 시각을 밖에서 넣어야 자정 넘김·긴 초과·앱 중단 복구를 테스트로 재현할 수 있다.

2.3. `render/`는 상태를 읽어 화면을 갱신하고 상태를 바꾸지 않는다.

2.4. `store/repo.js`만 저장에 손댄다. `core/`와 `render/`는 저장을 모른다.

2.5. `platform/`은 브라우저 사정(화면 꺼짐·음성·시각)을 가두는 자리다. 이 세 파일 밖에서 `wakeLock` · `speechSynthesis` · `Date.now`를 직접 부르지 않는다. 고도 같은 다른 바탕으로 옮길 때 갈아 끼울 자리가 여기 하나로 모인다.

2.6. `render/runView.js`만 `input/`을 직접 문다. 짧게·길게 누름을 가르는 자리가 다음 버튼 하나뿐이라, 그 버튼을 만드는 쪽에서 붙이는 편이 `main.js`가 남의 화면 속 버튼을 찾아 붙이는 것보다 짧다. 다른 화면이 같은 입력을 쓰게 되면 그때 `main.js`로 올린다(2026-09-17 추가).

## 3. 공용 자산 사용

3.1. 쓰는 것.

| 자산 | 쓰는 자리 | 비고 |
|---|---|---|
| `shared/tokens.css` | 색·간격·최소 터치 크기의 이름 | 값은 이 앱 토큰이 덮어쓴다 (3.7) |
| `shared/base.css` | 화면 바탕과 공통 버튼 (`mobile-shell.css`를 안에서 불러온다) | 토큰 이름으로 쓰므로 밝은 톤에서도 그대로 돈다 |
| `shared/storage.js` | `createStorage("todayfit")` | 3.2 참조 |
| `shared/ui.js` | `showModal` · `showToast` · `registerServiceWorker` | 확인 창과 알림 |
| `shared/frame/audio.js` | `createAudio` → 비프음 | 3.4 참조 |
| `shared/cloud/auto.js` | `index.html`에서 script로 로드 | 화면 없이 동기화만 |

3.2. **저장은 `createStorage("todayfit")` 경유다.** `localStorage`를 직접 부르지 않는다. 공용 저장기는 쓰기마다 슬롯 변경 시각을 찍고 클라우드 동기화에 알리는데, 직접 접근하면 그 신호가 끊겨 다른 기기와 어긋난다.

3.3. **`shared/cloud/policy.js`에 이 앱 항목을 추가해야 한다.** 새 앱이 저장을 가지면 계정에 올리지 않을 키와 합칠 항목을 그 표에 적는다.

- 올리지 않을 키 - `active`(진행 중 세션). 어느 기기에서 운동 중인지는 그 기기의 상태이고, 다른 기기로 넘기면 같은 세션이 둘로 갈린다
- 합칠 항목 - **1차에서는 두지 않는다.** 공용 병합이 가진 종류는 배열·값 모음·숫자 맵 셋인데, 이 앱의 `sessions`와 `plans`는 날짜를 키로 하고 값이 덩어리라 셋 중 어디에도 맞지 않는다. 종류를 새로 더하는 것은 전 앱 공통 자산을 바꾸는 일이라 이 앱 혼자 결정하지 않는다
- 따라서 1차의 다기기 동작은 공용 기본값인 **최신 저장 우선**이다. 한 기기만 쓰는 동안에는 드러나지 않고, 두 기기에서 같은 날 각각 운동하면 나중 것이 이긴다. 두 기기 사용이 실제로 생기면 그때 병합 종류 신설을 사용자 결정으로 올린다

3.4. 비프음은 `shared/frame/audio.js`의 `createAudio`를 쓴다. 게임 프레임의 다른 부품(타이틀 화면·상점·지갑·진행맵)은 쓰지 않는다. 이 파일만 따로 쓰는 이유는 3.5의 소리 잠금 해제를 이미 풀어 두었기 때문이다.

3.5. 게임 프레임 전체(`shared/frame/index.js`의 `createGameFrame`)는 쓰지 않는다. 앱 셋(영어 독해·영어 단어장·lotto)이 전부 쓰지 않으며, 이 앱도 시작 화면·되돌아가기 계단·재화가 없다.

3.6. 허브로 나가는 링크는 앱이 직접 둔다(`<a href="../../">`). 앱들의 공통 관행이다.

3.7. **밝은 톤은 `styles/tokens.css`가 `:root`에서 토큰 값을 덮어써 낸다.** `shared/tokens.css` 다음에 링크해 값만 갈아 끼우고, 토큰 이름과 `shared/base.css`는 그대로 쓴다.

- 스도쿠는 `.page.sudoku` 스코프에서 덮어쓰는데, 화면 위로 뜨는 팝업이 `body` 바로 아래 붙어 그 스코프 밖이라 팝업 색을 손으로 다시 적어야 했다(`games/sudoku/style.css` 349~367줄). 색값이 코드에 직접 박히는 자리가 그렇게 생겼다
- 이 앱은 페이지 전체가 밝은 톤이므로 스코프를 좁힐 이유가 없다. `:root`에서 덮어쓰면 팝업도 같은 값을 물려받아 그 흠이 생기지 않는다
- 허브와 다른 앱에는 영향이 없다. 각 앱이 자기 문서에서만 이 파일을 링크한다

## 4. 설계 시 검토 여섯의 결론

기획서 7.9가 설계로 넘긴 항목이다. 아래가 그 답이다.

### 4.1. 진행 상태 저장

4.1.1. `store/repo.js`가 `createStorage("todayfit")` 위에서 `active` 키 하나에 진행 중 세션을 통째로 쓴다.

4.1.2. 쓰는 시점은 `01_spec.md` 8.1의 여덟 자리다. 매 틱마다 쓰지 않는다 - 구간이 바뀔 때만 쓴다.

4.1.3. 구간 안의 경과는 저장하지 않고 `phaseStartedAt`과 `phaseElapsedBefore` 둘로 복원한다. 초 단위로 쓰기를 반복하면 저장 장치를 계속 두드리게 되고, 복원에 필요한 것은 구간 진입 시각뿐이다.

4.1.4. 앱이 닫히면 마지막 저장 지점으로 되살아나므로, `01_spec.md` 4.5.2대로 운동 구간은 그 세트 처음부터 시작한다.

4.1.5. 휴식·전환의 남은 시간을 살리려고 `visibilitychange`와 `pagehide`에서 한 번 더 쓴다. 이 두 자리가 실제 종료의 대부분을 잡는다 - 탭을 닫거나 다른 앱으로 넘어가거나 화면을 잠글 때 모두 불린다. 그래도 못 잡는 딱딱한 중단에서는 그 구간을 처음부터 하며, 쉬는 시간을 더 주는 쪽이라 안전한 쪽으로 틀어진다.

### 4.2. 화면 꺼짐 방지

4.2.1. `platform/wakelock.js`가 Screen Wake Lock을 감싼다. 이 저장소에서 처음 쓰는 기능이라 참고할 기존 자리가 없다.

4.2.2. 운동 실행 화면에 들어갈 때 요청하고 나올 때 푼다.

4.2.3. 화면이 잠기거나 다른 앱으로 넘어가면 잠금이 저절로 풀린다. 돌아왔을 때 `visibilitychange`에서 다시 요청한다.

4.2.4. 지원하지 않는 브라우저에서는 조용히 넘어간다. 화면이 꺼져도 앱은 멈추지 않고, 돌아오면 `01_spec.md` 4.5의 복구 규칙이 받는다.

4.2.5. **이 기능으로 화면 꺼짐을 완전히 막지는 못한다.** 사용자가 전원 버튼을 누르면 풀린다. 기획서 1.1의 "화면을 켠 채 거치한다"는 전제가 그래서 있다.

### 4.3. 길게 누르기

4.3.1. `input/pressInput.js`가 `pointerdown`에서 `LONG_PRESS_MS` 타이머를 걸고, 그 타이머가 먼저 울리면 길게·손을 먼저 떼면 짧게로 가른다. **손을 떼야 판정하는 방식이 아니다** - 누르고 있는 채로 판정 시간이 지나면 그 자리에서 건너뛰기가 걸린다. 운동 중에는 눌렀는데 아무 반응이 없는 시간이 길수록 사용자가 더 누르게 되므로, 즉시 반응하는 쪽으로 두었다(2026-09-17 구현 시 확정).

4.3.2. `contextmenu`를 `preventDefault`로 막는다. 같은 패턴이 지뢰찾기와 노노그램의 판 입력에 있다.

4.3.3. 글자 선택과 탭 강조는 `shared/base.css`가 불러오는 `mobile-shell.css`가 이미 막는다. 앱에서 다시 선언하지 않는다.

4.3.4. 길게 누름이 걸린 뒤에는 뒤따르는 `click`을 흘린다. 길게 눌러 건너뛴 다음 짧게 누름까지 먹어 두 구간이 한 번에 지나가는 사고를 막는다.

### 4.4. 소리 잠금 해제

4.4.1. `shared/frame/audio.js`의 `createAudio`가 `autoUnlock`으로 첫 `pointerdown`·`touchend`·`keydown` 한 번에 소리 장치를 연다. 이 앱에서는 오늘 화면의 `운동 시작` 조작이 그 첫 손짓이 된다.

4.4.2. 음성도 같은 손짓에서 한 번 깨운다. 빈 문장을 한 번 읽혀 두면 그 뒤의 안내가 막히지 않는다.

4.4.3. 소리 장치는 4초 무음이면 스스로 쉬고 다음 소리에서 깨어난다(`shared/frame/audio.js`가 그렇게 만들어져 있다). 휴식 30초 같은 긴 침묵 뒤의 첫 비프가 잘리지 않도록 예약 재생을 쓴다.

### 4.5. 음성 안내 생성

4.5.1. `platform/speech.js`가 브라우저 음성 합성을 감싼다. 문구는 `src/data/phrases.js`가 갖고, 코드에 문장을 직접 적지 않는다.

4.5.2. 언어는 `ko-KR`, 속도는 `02_data.md` 6장 값이다. 새 안내를 내기 전에 앞 안내를 끊는다 - 세트가 빨리 지나갈 때 안내가 밀려 쌓이면 지금 상태와 어긋난다.

4.5.3. **한국어 음성이 없는 기기가 있다.** 목록에 한국어가 없으면 음성을 끄고 비프음만 낸다. 이 경우 화면의 음성 설정 항목에 쓸 수 없음을 표시한다. **표시 자리인 기본값과 소리 화면(S-11)은 아직 없어, 지금은 소리를 내지 않는 것까지만 돈다**(2026-09-17).

4.5.4. 운동명은 사용자가 지은 이름이라 발음이 어긋날 수 있다. 1차에서는 발음 교정을 두지 않는다.

4.5.5. 음성 실패가 진행을 막지 않는다. 전체를 감싸 삼키고 구간은 그대로 돈다. 영어 단어장이 같은 방식이다.

### 4.6. 오프라인

4.6.1. 오프라인은 루트 `service-worker.js` 하나가 맡는다. 앱별 작업자를 새로 만들지 않는다.

4.6.2. 이 앱 자산은 미리 담는 목록에 넣지 않고 첫 방문 때 담기게 둔다. 앱 셋이 모두 같다.

4.6.3. 이 앱은 함께 배포하는 데이터 파일이 없다. 운동 종목과 계획을 전부 사용자가 만들어 기기에 담으므로, 첫 방문 뒤에는 통신 없이 돈다.

4.6.4. 배포할 때 `service-worker.js`의 판 번호를 올린다. 올리지 않으면 예전 화면이 남는다.

## 5. 데이터 흐름

5.1. 계획 만들기 - 요일 규칙 + 루틴 + 운동 템플릿 + 앱 설정 → `core/resolve.js`가 값을 확정 → `core/planner.js`가 그 달 날짜별 계획 생성 → `store/repo.js`가 `plans`에 저장.

5.2. 운동 실행 - `plans`의 그날 계획 → 스냅샷 복사 → `core/session.js`가 상태 기계로 진행 → 구간이 바뀔 때마다 `store/repo.js`가 `active`에 저장 → 종료 시 `sessions`로 확정하고 `active` 삭제.

5.3. 화면 표시 - `store/repo.js`가 읽은 값 → `core/dayStatus.js`·`core/stats.js`가 계산 → `render/*`가 그린다. 상태 없음·예정·미실시는 저장하지 않고 이 길에서 계산된다.

5.4. 같은 날 재개 - `sessions`의 그날 기록 → 남은 세트를 추려 `active`로 되돌림 → 5.2와 같은 길 → 종료 시 같은 기록에 덮어쓴다.

## 6. 테스트 경계

6.1. `core/` 전부가 단위 검사 대상이다. 브라우저 없이 돈다.

6.2. 반드시 덮는 것.

- 상태 기계 - 구간 전환 전량, 운동 구간이 시간으로 끝나지 않음, 마지막 운동 뒤 전환 없음
- 건너뛰기와 되돌리기 - 완료 세트 유지, 되돌린 뒤 잔여 시간 일치
- 앱 중단 복구 - 구간별 복구 지점, 닫힌 동안 구간이 지나가지 않음
- 같은 날 재개 - 건너뛴 운동 제외, 시각과 누적 시간 처리, 재개 후 완료 전환
- 자정 경계 - 네 경우 전부 (`01_spec.md` 5.6)
- 값 적용 순서 - 3단 사다리 전 갈래
- 집계 - 도래 계획 일수, 분모 0, 주 경계(월~일)
- 예상 총 운동시간 - 운동 1개, 세트 1개 같은 모서리

6.3. `run-node.js`는 `localStorage` 대역을 주입한다. lotto의 같은 파일이 선례다.

6.4. 루트 `tests/smoke.mjs`가 `apps/_registry.json`을 돌며 각 앱 `index.html`의 공용 뼈대와 화면 설정을 검사한다. 등록하면 자동으로 걸린다.
