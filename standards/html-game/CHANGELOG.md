# html-game 표준 변경 이력

# 1. v0.3.4 (2026-07-31)

1.1. 4.7 규칙 6 보강: 전체화면이 막힌 기기(아이폰)에서 버튼을 조용히 감추는 처리를 금지. 버튼을 남겨 누르면 홈 화면 추가 안내를 띄우고, 허브 첫 화면에서도 첫 방문 1회 알린다. 공용 구현 `shared/fullscreen.js`의 `showHomeScreenHint`·`homeScreenHintText`(브라우저별 경로 문구 분기).
1.2. 변경 사유: 사용자가 "아이폰 크롬에서는 전체화면이 안 된다"고 보고. 진단 결과 우리 결함이 아니라 애플 정책이었다 - 아이폰은 동영상 외 전체화면을 열지 않고, 아이폰의 모든 브라우저가 Safari 엔진을 쓰도록 강제돼 크롬으로 바꿔도 같다. v0.3.3 구현은 그런 기기에서 버튼을 감췄고, 사용자에게는 "안 된다"로만 보여 유일한 대안(홈 화면 추가)에 도달할 길이 없었다. 사용자가 "모든 사람이 쓰게 하고 싶다"고 결정해 화면 안 안내로 승격.
1.3. 검증: `tests/fullscreen.test.mjs` 10 → 14건(막힌 기기 버튼 유지·안내 연결 / 브라우저별 문구 분기 / 첫 방문 1회 / 중복 표시 방지 / 홈 화면 앱에서는 안내 없음) + smoke 정적 검사 3건 추가(29 통과). 아이폰 흉내 실브라우저 실측 - 허브 첫 방문 안내 표시·닫기 후 재방문 미표시, 게임 화면 버튼 유지 및 눌러 안내 표시, 홈 화면 앱 실행에서는 버튼·안내 모두 없음. 스크린샷 2장(라이트 허브·다크 게임)으로 대비·화면 안 배치 확인.
1.4. 영향: 허브 첫 화면 + 게임 5개(공용 모듈 경유 자동 적용). 아이패드·데스크톱은 전체화면이 지원되므로 안내가 뜨지 않아 무영향.
# 2. v0.3.3 (2026-07-31)

2.1. 4.7 규칙 6 강화: "전체화면" → "전체화면 - 켜는 것보다 유지가 어렵다". 버튼 제공·미지원 숨김에 더해, 브라우저가 조작 중 임의로 해제한 것을 감지해 다음 사용자 조작에서 되돌리도록 의무화. 사용자가 버튼·ESC로 끈 것은 되돌리지 않는다. 구현은 게임별 재작성 금지, 공용 모듈 `shared/fullscreen.js` 사용.
2.2. 4.7 규칙 8 신설: "홈 화면 앱 실행". 게임 화면마다 자기 `app.webmanifest`(display: fullscreen / start_url './' / scope 허브 루트) + `apple-mobile-web-app-capable`. 허브 첫 화면에만 두면 게임 화면에서 홈 화면에 추가할 때 브라우저 껍데기가 붙어 열린다.
2.3. 변경 사유: 사용자가 아이패드에서 전체화면으로 플레이해도 조작 중 금방 풀린다고 보고. 원인 둘 - (a) 아이패드 Safari·Chrome이 가장자리 스와이프·여러 손가락 제스처·회전에 전체화면을 스스로 끝내는데 기존 구현은 해제를 감지하지 않아 사용자가 버튼을 다시 눌러야 했다. (b) 우회로인 홈 화면 추가도 게임 화면 다섯 곳에 manifest 링크가 없어 반쪽이었다(노노그램은 애플용 표식도 없었다).
2.4. 검증: `tests/fullscreen.test.mjs` 10건 신설(복귀·사용자 의사 존중·재시도 한도·접두 API·홈 화면 앱 판별) + `tests/smoke.mjs` 정적 검사 확장(공용 모듈 사용 강제·옛 인라인 구현 부활 차단·8개 화면 홈 화면 앱 설정). 실브라우저(Chrome) 신뢰 입력 실측 - 전체화면 진입 → 강제 해제 → 조작 후 자동 복귀 확인, 버튼으로 끈 뒤에는 복귀하지 않음.
2.5. 영향: 게임 5개 + 앱 3개에 적용(공용 모듈 배선 + app.webmanifest). 적용 프로젝트 lotto는 표준 대상이라 v0.3.2 → v0.3.3 마이그레이션 여부 사용자 결정(3.2 절차). 아이패드 실기기 체감은 사람만 측정 가능 - 사용자 실측 대기.

# 3. v0.3.2 (2026-07-06)

3.1. 4.7 규칙 7 강화: "보드 크기 산정" → "창 비율 무관 전체 fit". 가용 폭 계산에 보드 옆 UI 열 폭까지 포함하고, 어느 한 축을 병목에서 제외하는 구현을 금지. 창/뷰포트 비율이 어떻든 게임 UI 전체가 스크롤·잘림 없이 한 화면에 들어와야 한다.
3.2. 변경 사유: 사용자가 데스크톱에서 창을 옆으로 넓게(가로 판정 비율) 배치하자 노노그램 보드+좌우 UI가 화면 폭을 넘어 좌우가 잘림. 원인은 가로 방향에서 폭을 병목에서 제외(무한대)한 fitBoard 구현 - 규칙 7이 "폭·높이 둘 다"라고만 적고 주변 UI 폭 포함을 명시하지 않아 생긴 틈.
3.3. 검증: 노노그램 fitBoard가 가로 방향에서 화면 폭 - 좌우 UI 열 - 열 간격을 가용 폭으로 반영. 사용자 재현 창 크기(1077×858) browser-shot으로 잘림 0 확인.
3.4. 영향: nonogram v0.3.1 → v0.3.2. 다른 게임은 마이그레이션 필요 여부 사용자 결정(3.2 절차).

# 4. v0.3.1 (2026-07-05)

4.1. 4.7 규칙 1-4의 무테마 골격을 공용 자산 `shared/mobile-shell.css`로 실제 분리. 색·폰트 없이 뷰포트 고정·safe-area·터치·리셋만 담는다. base.css는 이 파일을 `@import`(다크 테마 게임 무영향), 자체 디자인 게임은 직접 링크.
4.2. 변경 사유: 4.7 규칙은 글로 있었으나 구현이 base.css(다크 테마 한 덩어리)에만 있어, 파스텔 게임(노노그램)이 뷰포트 골격 값을 복붙해 중복. 색과 무관한 골격을 무테마 파일로 떼어 링크 재사용이 가능하게 함.
4.3. 검증: 노노그램 main.css 복붙 구간 제거 + mobile-shell.css 링크 전환. browser-shot으로 노노그램(파스텔 배경·맵 정상) + base.css 링크 게임 러시아워(다크 배경·`@import` 정상) 렌더 무변화 확인, pageerror 0.
4.4. 영향: nonogram v0.3 → v0.3.1(복붙 → 링크 전환). tetris/sudoku/rushhour/허브는 base.css가 mobile-shell을 `@import`하므로 무영향(마이그레이션 불필요).

# 5. v0.3 (2026-07-05)

5.1. 4.7 신설: 모바일/태블릿 브라우저 플레이 규칙 7개(viewport meta / 페이지 고정 / safe-area / 드래그 스크롤 차단 / 방향별 레이아웃 / 전체화면 / 보드 크기 산정).
5.2. 변경 사유: 사용자가 아이패드 크롬에서 노노그램 플레이 시 상단 UI가 브라우저 툴바에 잘리고 드래그 시 게임판이 스크롤되는 문제를 지적. 표준에 모바일 플레이 규칙이 전무해 게임별 재량으로 처리되며 편차가 컸음(base.css 미링크 게임은 규칙 누락). 웹게임 공통 규칙으로 명문화.
5.3. 검증: 노노그램에서 아이패드 프로 12.9"·11" 가로/세로 + 구형 아이패드 + 아이폰 6종 뷰포트로 스크롤 0·격자 중앙·safe-area·전체화면 확인, 테스트 20/20. base.css 검증값을 직접 이식(파스텔 자체 디자인이라 base.css 컴포넌트 통째 링크는 부적합).
5.4. 영향: nonogram v0.2 → v0.3 적용. tetris/sudoku/rushhour는 shared/base.css로 1-4를 이미 부분 준수하나 정식 마이그레이션은 사용자 결정(방향별 레이아웃·전체화면 미적용분 존재). lotto는 게임(추천기)이 아니라 대상 제외.
