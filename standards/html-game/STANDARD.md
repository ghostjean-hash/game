## 1. 프로젝트 개요

GitHub Pages로 호스팅하는 정적 HTML 게임을 만든다. 빌드 시스템 없이 브라우저가 ES Modules를 직접 실행하는 방식.

작업 방식은 문서 우선. 모든 요구사항은 문서를 먼저 수정하고, 그에 따라 코드를 작성한다. 문서가 진실의 원천(SSOT)이다.

## 4. 절대 규칙

### 4.1. 문서 우선 워크플로우

- 사용자 요구사항 → 영향받는 문서 식별 → 문서 수정 → 코드 수정 → 테스트 수정 순서.
- 문서와 코드가 충돌하면 문서가 진실. 코드를 문서에 맞춤.
- 같은 정보를 두 문서에 적지 않는다. 한 곳만 SSOT, 나머지는 "→ 해당 문서 참조".

### 4.2. 기술 환경

- 빌드 시스템 없음. ES Modules 직접 사용 (`<script type="module">`).
- import는 상대경로 + `.js` 확장자 명시.
- TypeScript, 번들러, 트랜스파일러, npm 설치 금지.
- 외부 라이브러리는 가능한 vanilla로. 불가피하면 esm.sh / jsdelivr CDN의 ESM 빌드만.
- 폴리필 사용 안 함. 최신 Chrome / Safari / Firefox 기준.

### 4.3. 코드 구조

- `core/`는 DOM, Canvas, window, document 일체 import 금지. 순수 함수 위주.
- 게임 로직과 렌더링은 절대 한 모듈에 두지 않는다.
- 매직 넘버 금지. 모든 수치는 정의된 상수에서 가져옴.

### 4.4. 색상과 스타일

- 게임 데이터(블록 색, 이펙트 색 등 게임 플레이의 일부): `src/data/colors.js`의 상수만 사용.
- 디자인 토큰(메뉴 / HUD 색, 간격, 폰트 등 UI 요소): `styles/tokens.css`의 CSS 변수만 사용.
- 인라인 매직 값 금지. 필요하면 정의 위치에 먼저 추가 후 사용.

### 4.5. 데이터 저장

- 영속 데이터는 localStorage. 키 prefix는 게임명 (예: `tetris_`).
- 저장 스키마는 `docs/02_data.md`에 정의.

### 4.6. 테스트

- 브라우저 기반 테스트. `tests/test.html`을 열면 모든 테스트 자동 실행.
- `core/` 모듈은 테스트 필수. 특히 게임 핵심 로직 변경 시 반드시 테스트 함께 수정.

### 4.7. 모바일/태블릿 브라우저 플레이 규칙

핸드폰·태블릿 브라우저에서 플레이하는 게임은 아래를 지킨다(노노그램에서 검증, v0.3 신설 2026-07-05). 규칙 1-4의 무테마 골격(색·폰트 없이 뷰포트 고정·safe-area·터치·리셋만)은 공용 자산 `shared/mobile-shell.css`가 제공한다(v0.3.1 실제 분리). 다크 테마 게임은 `shared/base.css`를 링크하면 되고(base.css가 mobile-shell.css를 `@import`), 자체 디자인 게임(파스텔 톤 등)은 `shared/mobile-shell.css`를 직접 링크한 뒤 자기 색·폰트만 얹는다. 규칙 값을 복사하지 않는다.

1. **viewport meta**: `width=device-width, initial-scale=1, viewport-fit=cover`. 게임판을 드래그로 조작하는 게임은 `maximum-scale=1, user-scalable=no`로 확대를 잠근다. `viewport-fit=cover`가 있어야 safe-area가 동작한다.
2. **페이지 고정**: `html { overflow:hidden }`, `body { height:100dvh; overscroll-behavior:none; touch-action:manipulation }`. 페이지 자체가 세로 스크롤·고무줄 바운스·더블탭 확대되지 않게 뷰포트에 고정한다. `100vh`가 아니라 `100dvh`(모바일 주소창 변화 대응).
3. **safe-area**: `body`에 `env(safe-area-inset-*)` 패딩. 노치·홈바에 UI가 가리지 않게 안전 영역 안에만 둔다.
4. **드래그 스크롤 차단**: 게임판(드래그 조작 영역)은 `touch-action:none`, 게임판을 감싼 컨테이너는 `overflow:hidden`. 드래그해도 판이 좌우·상하로 밀려 스크롤되지 않는다. 목록이 긴 화면(맵·결과 등)만 그 화면의 내부 컨테이너에서 스크롤한다(`overflow-y:auto`) - 페이지가 아니라 그 안에서.
5. **방향별 레이아웃**: 세로에서는 UI를 위·아래로, 가로에서는 좌·우로 분산 배치하고 게임판을 화면 중앙에 둔다(`@media (orientation:landscape)`로 재배치). 가로에서는 세로 폰 기준 폭 제한(`max-width`)을 풀어 넓은 화면을 활용하고, 좌·우 UI 열을 같은 폭으로 맞춰 게임판이 정중앙에 오게 한다.
6. **전체화면 - 켜는 것보다 유지가 어렵다**: 지원 기기에서 Fullscreen API 토글 버튼을 제공한다. 아이폰처럼 전체화면 자체가 막힌 기기에서는 **버튼을 조용히 감추지 않는다** - 감추면 사용자는 "왜 없지"로 끝나므로, 버튼을 남겨 누르면 유일하게 통하는 길(규칙 8의 홈 화면 추가) 안내를 띄우고 허브 첫 화면에서도 첫 방문 1회 알린다(v0.3.4). **안내는 글만으로 쓰지 않는다** - 일반 사용자는 글 설명으로 어느 버튼인지 찾지 못하므로, 눌러야 할 버튼 모양을 그린 단계 그림과 그 도구 모음 방향을 가리키는 화살표를 함께 둔다. 버튼 위치가 브라우저마다 달라 그림·문구·화살표 방향을 브라우저별로 갈라 쓴다(사파리 = 아래 도구 모음 가운데, 아이폰 크롬 = 주소창 오른쪽 메뉴, v0.3.5). 아이폰은 애플이 동영상 외 전체화면을 열지 않았고 아이폰의 모든 브라우저가 Safari 엔진을 쓰도록 강제돼 Chrome으로 바꿔도 같다 - 기기 문제이므로 안내가 유일한 처방이다. 여기서 끝내면 안 된다 - 브라우저는 전체화면을 임시 상태로 다뤄 조작 도중 스스로 끝낸다(아이패드 Safari·Chrome의 가장자리 스와이프·여러 손가락 제스처·회전). 해제를 감지해 **다음 사용자 조작(손 뗌·키 입력)에서 되돌린다**. 전체화면 진입은 사용자 조작 안에서만 허용되므로 조작 없는 즉시 복귀는 불가능하고, "한 번 더 만지면 돌아온다"가 규격상 상한이다. 사용자가 버튼·ESC로 직접 끈 것은 되돌리지 않는다. 게임마다 새로 만들지 말고 공용 모듈 `shared/fullscreen.js`를 쓴다(접두 API·재시도 한도·홈 화면 앱 판별 포함, v0.3.3).
7. **보드 크기 산정 - 창 비율 무관 전체 fit**: 셀/보드 크기는 뷰포트 폭·높이를 둘 다 재서 남는 공간에 맞춘다(폭만 기준으로 하면 가로 방향에서 높이를 넘겨 스크롤이 생긴다). 가용 폭에는 보드 옆에 놓이는 UI 열(버튼·상태 표시) 폭까지 포함해 뺀다 - 어느 한 축을 "병목 아님"으로 가정하면(예: 가로에서 폭 무시) 데스크톱 창 리사이즈처럼 임의 비율 창에서 게임이 화면 밖으로 잘린다. 창/뷰포트 비율이 어떻든 게임 UI 전체가 스크롤·잘림 없이 한 화면에 들어와야 한다(노노그램 가로 창 좌우 잘림 사례, v0.3.2). 방향 전환·리사이즈·전체화면 전환 시 재계산한다.
8. **홈 화면 앱 실행 - 전체화면 유지의 근본 처방**: 게임 화면마다 자기 `app.webmanifest`(`display: fullscreen`, `start_url: "./"`, `scope`는 허브 루트)를 링크하고 `apple-mobile-web-app-capable`을 함께 둔다. 허브 첫 화면에만 설정을 두면 게임 화면에서 홈 화면에 추가했을 때 브라우저 껍데기가 붙은 채 열린다. 홈 화면 앱으로 실행하면 주소창·탭바가 애초에 없어 전체화면이 풀릴 여지 자체가 사라지고, 규칙 6의 자동 복귀는 그때까지 버티는 보정이다. 이 상태에서는 전체화면 버튼을 감춘다(v0.3.3 신설).

### 4.8. 게임 시작 흐름 (공용 프레임)

게임을 연 순간부터 플레이가 시작될 때까지의 화면 구성과 이동 규칙은 모든 게임이 똑같이 쓴다(v0.4 신설 2026-08-01). 규격 본문과 화면 그림은 기획서 `plans/doc/screen-frame.html`(Ⅰ권)이 SSOT이고, 여기에는 코드에서 지킬 규칙만 적는다. 구현체는 공용 자산 `shared/frame/`이며 게임마다 새로 만들지 않는다.

1. **다섯 화면 고정**: 인트로 · 시작 화면 · 플레이 · 잠깐 멈춤 · 결과. 순서는 바뀌지 않는다. 시작 화면과 플레이는 어떤 게임도 생략할 수 없다. 인트로는 지금 다섯 게임 모두 쓰지 않는다(2026-08-01 결정, 자리는 규격에 남겨 무거운 게임이 나올 때 다시 판단). 판이 수백 개인 게임은 시작 화면과 플레이 사이에 판 고르는 화면 한 칸을 넣는다.
2. **화면 전환은 이름으로 가른다**: 지금 어느 화면인지를 뿌리 요소 한 곳에 적고 CSS가 그 값만 보고 표시를 정한다. 요소마다 숨김 속성을 켜고 끄는 방식은 새 게임에 쓰지 않는다 - 숨기라는 지시가 배치 지시에 밀려 두 화면이 겹쳐 보이는 사고가 실제로 있었다. 주소를 바꿔 페이지를 새로 읽는 방식도 쓰지 않는다.
3. **되돌아가기 계단**: 화면이 한 칸 깊어질 때마다 되돌아갈 자리를 하나 쌓고, 되돌아가기는 한 칸만 올라간다. 화면 왼쪽 위 화살표와 기기 자체의 되돌아가기 동작이 같은 결과를 내야 한다. **플레이 중에 허브로 곧장 나가는 문을 어디에도 두지 않는다** - 게임을 닫는 지점은 시작 화면 하나뿐이다. 계단은 게임이 개별로 쌓지 않고 공용 자산이 일괄 관리한다.
4. **상단 띠 세 구역**: 왼쪽은 되돌아가기 하나만, 가운데는 시작 화면에서 비우고 플레이에서 점수·진행, 오른쪽은 환경설정 · 소리 · 전체화면 · 잠깐 멈춤 순서로 고정한다. 소리 버튼은 모든 게임에 반드시 있다. 게임 이름을 띠에 적지 않는다(시작 화면 큰 글자가 담당).
5. **시작 화면 규격**: 배경과 캐릭터가 화면 위쪽을 다 쓰고 누르는 것은 전부 아래 조작단에 모인다. 칸 순서는 이어서 하기 → 고르는 칸이나 옵션 → 시작이며, 시작이 가장 크고 강조된 하나다. 갈래가 여러 개면 카드를 펼치지 않고 고르는 칸 하나로 접는다(첫 화면 높이가 갈래 수에 흔들리지 않게). 게임 고유 화면(상점·도감)은 새 칸을 만들지 않고 조작단 맨 아래 한 줄에 나란히 둔다.
6. **화면 문구 고정**: 시작 / 이어서 하기 / 계속하기 / 다시 하기 / 그만하기 / 환경설정. 같은 뜻을 게임마다 다르게 쓰지 않는다. 문구는 `shared/frame/text.js` 한 곳에 있고 `tests/frame.test.mjs`가 기획서 표와의 일치를 지킨다.
7. **전체화면이 막힌 기기 기준으로 만든다**: 시작 화면은 화면을 다 쓰는 경우가 아니라 브라우저 창이 먹는 경우를 기준으로 짠다(규칙 4.7-6 참조). 조작단 맨 아래 버튼과 화면 끝 사이 여백은 공용 자산이 일괄 관리하고 게임이 각자 정하지 않는다. 세로 스크롤이 생기면 규격 위반으로 보고 항목을 접어 해결한다.
8. **결과는 덮는 카드 하나로**: 알림창·전용 화면·덮어쓰는 창으로 갈려 있던 것을 플레이를 덮는 카드로 통일한다. 이번 점수, 최고 기록과의 비교, 다시 하기, 그만하기를 담고 새 기록이면 눈에 띄게 알린다. 화면을 벗어났다 돌아오는 경우에도 잠깐 멈춤 상태가 되어 돌아왔을 때 이미 죽어 있는 일을 막는다.
9. **소리·진행 저장도 공용**: 게임마다 복사돼 있던 소리 코드는 공용 그릇(`shared/frame/audio.js`)을 쓰고 게임은 음색표만 준다. 진행 저장은 `shared/storage.js`를 감싼 `shared/frame/save.js`를 거친다 - localStorage를 직접 만지면 클라우드 동기화 신호가 끊긴다.
10. **적용 순서**: 공용 부품을 먼저 만들고(1단계), 게임 하나로 검증한 뒤(2단계, 노노그램), 나머지 넷에 순차 적용한다(3단계). 새로 만드는 게임은 1단계가 끝난 시점부터 이 규격을 지키는 것이 필수다.
11. **보드를 화면 가득 쓰는 게임의 상단 띠 예외**(v0.4.0 노노그램 검증에서 확인): 플레이 화면이 보드를 화면 가득 채우려고 UI를 네 모서리에 붙이는 구조인 게임은, 그 화면에서만 공용 상단 띠를 감추고 모서리 버튼을 공용 프레임에 연결한다. 띠를 얹으면 보드 높이가 줄고 가로 방향 좌우 재배치가 깨지기 때문이다. 이때도 **동작은 공용을 쓴다** - 되돌아가기는 계단을 따르고, 소리는 공용 소리·저장을 쓰며, 상태가 바뀌면 프레임이 게임 버튼 아이콘을 갱신한다. 자리만 게임이 정하고 규칙은 공용이 가진다. 시작 화면·판 고르는 화면에서는 예외 없이 규격 띠를 쓴다.
12. **자동 잠깐 멈춤은 잃을 것이 있는 게임만**(v0.4.0 확인): 화면을 벗어났을 때 자동으로 멈춤 상태가 되는 것은 시간이 흐르거나 죽을 수 있는 게임의 안전장치다. 실패도 시간 제한도 없는 게임에서는 돌아올 때마다 카드가 떠 방해만 되므로 끈다(`pauseOnHide: false`).
13. **결과 카드에는 글자 아닌 것도 온다**(v0.4.0 확인): 완성한 그림, 별점처럼 게임의 결과가 숫자·문장이 아닌 경우가 있다. 카드는 줄 목록뿐 아니라 게임이 만든 요소를 그대로 받을 수 있어야 하고, 버튼 문구도 그 게임의 흐름이 규격 문구와 뜻이 다를 때만 바꾼다(노노그램은 "다시 하기"가 아니라 "다음 그림"이다).
14. **넓은 화면에서 조작단 폭을 묶는다**(v0.4.0 확인): 태블릿 가로·데스크톱에서 버튼이 화면 끝까지 늘어나면 누르는 자리가 흩어진다. 조작단 안쪽 폭을 손에 맞는 크기로 제한하고 가운데 세운다. 칸 순서와 강조는 그대로다.
15. **강조 버튼 글자색은 게임이 정한다**: 강조 버튼 배경은 그 게임의 강조색이고, 그 위에서 읽히는 글자색은 팔레트마다 다르다(`--accent-fg`). 지정하지 않으면 페이지 배경색을 쓴다.
16. **켜고 끄는 것은 고르는 것과 다른 자리다**(v0.4.2 비행 슈팅 적용에서 확인): 난이도처럼 하나를 고르는 갈래는 한 줄 세그(`options`)로, 친구 동행·자동 플레이처럼 각자 켜지고 꺼지는 것은 시작 바로 위 한 줄(`toggles`)로 둔다. 둘을 한 부품으로 다루면 서로 배타가 아닌 것이 배타처럼 동작한다. 켜진 것은 강조색 테두리로 표시한다 - 아이콘 색만 바꾸면 켜졌는지 알기 어렵다.
17. **플레이 화면 HUD를 캔버스 위에 겹쳐 놓은 게임도 규격 띠를 쓰지 않는다**(v0.4.2 확인): 규칙 11과 같은 이유다. HUD가 화면 공간을 차지하지 않도록 캔버스 위에 띄운 게임에 규격 띠를 얹으면 그 띠가 다시 공간을 먹어 화면이 줄어든다. 그 화면에서만 띠를 감추고 게임 HUD의 버튼을 공용에 연결한다.
18. **게임이 자기 이동 기록을 직접 쌓고 있으면 먼저 걷어낸다**(v0.4.2 확인): 되돌아가기를 스스로 처리하던 게임에 공용 계단을 얹으면 기기 뒤로가기 한 번에 두 칸이 물러난다. 게임 쪽 기록 쌓기와 뒤로가기 가로채기를 지우고 계단 하나만 남긴다.

## 5. CLAUDE.md 템플릿

게임명과 한 줄 설명만 빈칸으로 두고, 나머지는 그대로.

```markdown
# [게임명]

## 1. 게임 한 줄
[한 문장 설명]

## 2. 작업 워크플로우 (반드시 지킬 것)
1. 사용자 요구사항을 받으면, 먼저 어떤 문서를 수정해야 하는지 식별
2. 해당 문서를 수정 (단 하나의 진실의 원천)
3. 변경된 문서 기반으로 코드 수정
4. 테스트 코드도 함께 수정

## 3. 문서 인덱스
- docs/01_spec.md - 게임 규칙, 조작, 화면 흐름
- docs/02_data.md - 게임 데이터, 수치, 색상
- docs/03_architecture.md - 폴더/모듈 구조, 의존성 규칙
- docs/04_conventions.md - 네이밍, 주석, 테스트, 토큰 규칙

## 4. 절대 규칙
- 게임 로직과 렌더링은 절대 한 모듈에 두지 않는다
- 매직 넘버 금지. 모든 수치는 docs/02_data.md 정의 상수에서
- core/는 DOM/Canvas/window/document 일체 import 금지
- 핵심 로직 변경 시 반드시 테스트 코드 업데이트
- docs와 코드가 충돌하면 docs가 진실. 코드를 docs에 맞춰 수정

## 5. 기술 환경
- ES Modules 직접 사용. 빌드/번들러/TypeScript 금지
- import는 상대경로 + .js 확장자 명시
- 외부 라이브러리 최소화. 필요시 CDN ESM 빌드만
- 영속 데이터는 localStorage, 키 prefix는 [게임명_]

## 6. 색상과 스타일
- 게임 데이터(블록 색 등): src/data/colors.js 상수만 사용
- 디자인 토큰(UI 색/간격/폰트): styles/tokens.css 변수만 사용
- 인라인 매직 값 금지

## 7. 실행
- 로컬: `python -m http.server` 후 localhost:8000
- 테스트: tests/test.html을 브라우저에서 열기
- 배포: main 브랜치 push → GitHub Pages 자동 배포

## 8. 변경 이력
- YYYY-MM-DD: html-game v<x.y> 적용 (초기 셋업)
```

## 6. 초기 작업 순서

각 단계 완료 후 보고.

6.1. 위 폴더 구조와 빈 파일들 생성 (`.nojekyll` 포함).
6.2. CLAUDE.md를 위 템플릿으로 작성 (게임명/설명은 비워두기).
6.3. 빈 index.html과 main.js로 "검은 화면이라도 뜨는지" 확인 가능한 최소 셋업 작성.
6.4. tests/test.html과 runner.js를 외부 라이브러리 없이 동작하는 최소 테스트 러너로 작성.
6.5. styles/tokens.css에 디자인 토큰 기본 골격 작성 (색 / 간격 / 폰트 변수, 빈 값이라도).
6.6. README.md에 로컬 실행법, GitHub Pages 배포법, 테스트 실행법 작성.
6.7. docs/ 4개 파일은 H1 제목과 섹션 골격만 작성 (내용은 게임 결정 후 채움).

## 7. 문서 비대화 대응 규칙

작업 진행 중 한 문서가 커지면 다음 순서로 대응한다. 임의로 분할하지 말 것.

7.1. 먼저 압축 시도: 중복 제거, 결정 외 맥락 제거, 산문을 표로.
7.2. 데이터를 코드로 분리: 수치 표가 길면 `src/data/*.js`로 빼고 문서엔 스키마와 경로만.
7.3. 그래도 한 문서가 500줄을 넘고 변경 빈도가 명확히 갈리면 해당 문서만 폴더로 분할.

예: `docs/02_data.md` → `docs/02_data/` 폴더 + `_index.md` + 분할 파일들.
- 다른 문서는 단일 파일 유지.
- 분할 시 CLAUDE.md 인덱스 동기화 필수.

## 8. 게임 컨셉 결정 단계

위 셋업 완료 후, 다음 항목을 사용자에게 질문해서 `docs/01_spec.md`와 `docs/02_data.md`를 채운다. 사용자 답변 전에 임의 결정 금지.

8.1. 게임 장르와 한 줄 컨셉.
8.2. 핵심 메커닉 (코어 루프).
8.3. 조작 방식 (키보드 / 마우스 / 터치).
8.4. 성공 이벤트 / 실패 이벤트 / 종료 조건 (해당 없음 가능).
- 통상 게임 예: 클리어 = 성공, 게임오버 = 실패, 종료 = 클리어 시점.
- 추천기 / 시뮬레이션 예: 적중 = 성공 이벤트, 실패 없음, 종료 없음.
- 컬렉션 게임 예: 도감 채우기 = 성공, 실패 없음, 종료 없음.
8.5. 진행 시스템 (스테이지 / 스코어 / 시간 등).
8.6. 모바일 지원 여부.
