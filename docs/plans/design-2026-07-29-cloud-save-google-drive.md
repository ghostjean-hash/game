# 구글 드라이브 세이브 동기화 설계 (계획, 구현 착수 전)

> 작성 2026-07-29. 상태: **계획 확정 대기**. 이 문서 승인 전 코드 변경 0.
> 단일 진실 source (글로벌 CLAUDE.md 6.5). 구현 중 설계가 바뀌면 코드보다 이 문서를 먼저 고친다.

변경 영향 범위: **H** (전 게임·앱 7종의 저장 창구를 건드리고, 실패 시 기존 사용자 진행 데이터가 유실될 수 있다).

## 1. 목적과 범위

1.1. 목적: 기기·브라우저를 바꿔도 게임/앱 진행이 유지되게 한다. 서버는 운영하지 않는다.

1.2. 방식: 사용자가 자기 구글 계정으로 로그인하면, 그 사람 드라이브 안의 **이 웹사이트 전용 숨김 폴더**에 세이브가 저장된다. 데이터 소유자는 사용자 본인이고, 우리는 저장소를 갖지 않는다.

1.3. 사용자 확정 전제 (2026-07-29 대화)
- 1.3.1. 불특정 다수 공개. 사이트 방문자 누구나 로그인해 쓸 수 있어야 한다.
- 1.3.2. 서버 운영 금지. GitHub Pages 정적 호스팅 유지.
- 1.3.3. 저장 위치는 사용자 본인 드라이브.

1.4. 범위에 포함: 등록된 게임 6종(tetris / sudoku / lotto / rushhour / nonogram / flightshooting) + 앱 2종(english-reading / english-vocabulary)의 진행 데이터.

1.5. 범위 밖: 계정 간 데이터 공유, 순위표, 서버 검증, 결제. 지금 설계는 "내 데이터를 내 계정에 붙여둔다"까지다.

## 2. 권한 등급과 심사 (확인 완료)

2.1. 사용할 권한은 `drive.appdata` 하나. 이 웹사이트가 만든 숨김 폴더만 읽고 쓴다. 사용자의 기존 드라이브 파일은 목록조차 못 본다.

2.2. 구글 분류상 **민감하지 않은 권한(non-sensitive)** 이다. 민감하지 않은 권한만 쓰는 앱은 검증 절차 완료 의무가 없다 (출처: [Choose Google Drive API scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [OAuth App Verification Help Center](https://support.google.com/cloud/answer/13463073?hl=en)).

2.3. "확인되지 않은 앱" 경고는 민감·제한 권한을 심사 전에 요청할 때 뜬다. 우리 조합에서는 뜨지 않는다 (출처: [Unverified apps](https://support.google.com/cloud/answer/7454865?hl=en)).

2.4. 100명 제한은 심사가 아니라 콘솔 게시 상태가 "테스트 중"일 때 걸린다. "게시" 상태로 전환하면 풀린다.

2.5. **설계 불변 조건**: 권한을 `drive.appdata` 하나로 고정한다. `drive`(전체 접근)를 쓰는 순간 최고 등급인 "제한됨"이 되어 매년 외부 보안 감사가 붙는다. 코드 리뷰에서 이 권한 문자열이 늘어나면 즉시 반려한다.

2.6. 선택 사항: 로그인 창에 사이트 이름·로고를 띄우려면 "브랜드 확인"이라는 가벼운 별도 절차가 필요하다. 안 하면 주소만 표시된다. 동작에는 무관하므로 후순위.

## 3. 현재 상태 진단

3.1. **저장 창구가 이미 통일돼 있다.** tetris / sudoku / rushhour / nonogram / flightshooting / english-reading / english-vocabulary 7종이 전부 `shared/storage.js`의 `createStorage(네임스페이스)`만 거치고, 실제 키는 `gg.<네임스페이스>.*`로 자동 접두된다. 즉 파일 한 곳의 안쪽만 바꾸면 7종이 한꺼번에 편입된다.

3.2. **예외는 lotto 하나.** `games/lotto/src/data/storage.js`가 자체 접두 `lotto_`로 직접 읽고 쓴다. 다만 이 파일 안의 `read()` / `write()` 두 함수가 유일한 통로이고 "core에서 직접 접근 금지" 규율이 지켜지고 있어, 이 두 함수만 갈아끼우면 된다.

3.3. **서비스워커는 외부 요청을 안 건드린다.** `service-worker.js:199`가 `url.origin !== self.location.origin`이면 즉시 통과시킨다. 구글 로그인 스크립트와 드라이브 통신은 캐시 간섭을 받지 않는다. 다만 이건 현재 코드가 그렇다는 것이고, 검증 항목으로 남긴다(5.3.6).

3.4. **검증 인프라가 이미 있다.** `tests/smoke.mjs`(허브 정적 스모크, 순수 node), 앱별 `run-node` 테스트, `.claude/deploy.json`의 배포 파이프라인(테스트 → push → 실제 URL 스모크, 콘솔 에러 예산 0), `browser-shot` skill(실화면·콘솔 검사). 새 검증은 이 위에 얹는다.

## 4. 설계

### 4.1. 계층 분리 (검증 가능성이 설계를 결정한다)

구글 로그인은 사람이 버튼을 눌러야 해서 자동 테스트가 불가능하다. 그래서 **자동으로 검증할 수 있는 것을 최대한 많이 남기도록** 세 층으로 자른다.

| 층 | 파일(예정) | 하는 일 | 자동 검증 |
|---|---|---|---|
| 순수 로직 | `shared/cloud/merge.js` | 어느 쪽이 최신인지 판정, 세이브 묶음 병합, 형식 검사 | **100% 가능** (네트워크·브라우저 0) |
| 저장소 어댑터 | `shared/cloud/remote.js` | 세이브 문서를 올리고 내린다 | 가짜 저장소로 **가능** |
| 로그인 | `shared/cloud/auth.js` | 구글 로그인 창, 접속 토큰 관리 | 불가 (사람 체크리스트) |
| 조립 | `shared/cloud/sync.js` | 위 셋을 엮어 실제 동기화 수행 | 가짜 저장소 + 가짜 로그인으로 **가능** |

핵심: `merge.js`에는 `window`도 `fetch`도 등장하지 않는다. 순수 함수만 둔다. 데이터가 깨지는 사고는 거의 전부 이 층에서 나므로, 위험이 큰 부분을 자동 검증 100% 영역에 몰아넣는 것이 이 분리의 목적이다.

### 4.2. 세이브 문서 형식

드라이브 숨김 폴더에 파일 하나(`save-v1.json`)만 둔다. 게임마다 파일을 나누지 않는 이유는 요청 횟수와 충돌 지점을 줄이기 위해서다.

```
{
  "schema": 1,                       // 형식 버전. 올라가면 마이그레이션 경유
  "updatedAt": 1753747200000,        // 문서 전체 최종 갱신(참고용)
  "device": "chrome-win-9f2a",       // 어느 기기가 마지막에 썼는지(디버깅용)
  "slots": {
    "gg.tetris":        { "updatedAt": 1753740000000, "data": { "highscore": 12000 } },
    "gg.flightshooting":{ "updatedAt": 1753747200000, "data": { ... } },
    "lotto":            { "updatedAt": 1753700000000, "data": { ... } }
  }
}
```

4.2.1. **슬롯 = 게임 하나**. 게임별로 최종 갱신 시각을 따로 갖는다. 이게 있어야 "테트리스는 PC가 최신, 비행슈팅은 폰이 최신"인 상황에서 둘 다 살아남는다.

4.2.2. 슬롯 안의 `data`는 그 게임이 저장하던 키/값을 그대로 담는다. 게임 코드는 자기 데이터 모양을 바꾸지 않는다.

4.2.3. 문서 총량 상한을 둔다(예: 1MB). 넘으면 업로드를 중단하고 사용자에게 알린다. 조용한 실패 금지.

### 4.3. 동기화 규칙

4.3.1. **로컬 우선**. 게임은 지금처럼 기기 저장에 즉시 쓴다. 클라우드는 그 뒤를 따라간다. 네트워크가 끊겨도 게임은 평소대로 동작한다.

4.3.2. **올리기**: 저장이 발생하면 곧바로 올리지 않고 몇 초 모았다가(디바운스) 한 번에 올린다. 페이지를 떠날 때도 한 번 밀어낸다.

4.3.3. **내리기**: 로그인 직후, 그리고 페이지 진입 시 1회.

4.3.4. **충돌 판정** (슬롯 단위, 순수 함수)
- 한쪽에만 있으면 있는 쪽을 쓴다.
- 양쪽에 있고 시각이 다르면 최신을 쓴다.
- 시각이 같고 내용이 같으면 그대로 둔다.
- 시각이 같은데 내용이 다르면 **자동으로 덮지 않는다**. 사용자에게 "이 기기 기록 / 클라우드 기록" 중 선택을 묻는다.
- 로컬 시각이 클라우드보다 크게 미래면(기기 시계 오류) 자동 판정을 포기하고 역시 사용자에게 묻는다.

4.3.5. **첫 로그인**: 이미 이 기기에서 놀던 사람이 처음 로그인하면 로컬 기록이 있고 클라우드는 비어 있다. 이때는 로컬을 올린다. 반대로 클라우드에만 있으면 내린다. 양쪽 다 있으면 4.3.4를 슬롯마다 적용한다.

4.3.6. **로그아웃 시 로컬 데이터를 지우지 않는다.** 지우면 사용자가 진행을 잃는다.

### 4.4. 로그인과 토큰

4.4.1. 구글이 웹페이지용으로 제공하는 로그인 라이브러리를 `<script>` 한 줄로 불러온다. 빌드 도구·설치 없음.

4.4.2. 접속 토큰의 수명은 약 1시간이고 갱신 토큰은 브라우저 방식에서 발급되지 않는다. 만료되면 구글 세션이 살아 있는 한 창을 띄우지 않고 조용히 재발급한다.

4.4.3. 토큰은 메모리 + `sessionStorage`에만 둔다. `localStorage`에는 두지 않는다.

4.4.4. **각 게임이 별도 페이지라는 점이 이 설계의 최대 난점이다.** 허브에서 게임으로 이동하면 문서가 새로 뜨므로 토큰을 다시 얻어야 한다. 같은 출처라 `sessionStorage`는 공유되지만 만료 시점이 게임 도중에 올 수 있다. 대응: 게임 진입 시 조용한 재발급을 시도하고, 실패하면 **동기화만 끄고 게임은 그대로 진행**시킨다. 게임 중간에 로그인 창을 띄우지 않는다. 이 항목은 5.5의 실계정 체크리스트에서 반드시 확인한다.

### 4.5. 게임 편입 방식

4.5.1. `shared/storage.js`의 `createStorage()`는 **호출부 시그니처를 바꾸지 않는다**. 내부에서만 "저장할 때 동기화 큐에 알린다"를 추가한다. 따라서 게임 7종은 코드 수정 0.

4.5.2. lotto만 `games/lotto/src/data/storage.js`의 `read()` / `write()`에 같은 처리를 넣는다. 함수 2개.

4.5.3. 허브 `index.html`에 로그인 버튼과 상태 표시(마지막 동기화 시각)를 넣는다. 게임 화면 안에는 버튼을 넣지 않는다.

### 4.6. 동기화 제외 목록

용량이 크고 언제든 다시 받을 수 있는 데이터는 올리지 않는다. 진행 기록이 아니라 캐시이기 때문이다.

- `lotto_draws` (회차 전체 캐시. 원본을 다시 페치하면 복원된다)
- `lotto_stats_*` (draws에서 재계산되는 파생값)
- 서비스워커 캐시 일체

제외 목록은 코드에 상수로 두고, 5.2.9 테스트로 "제외 대상이 문서에 섞여 들어가지 않음"을 검사한다.

### 4.7. 화면 설계

원칙: 눈에 보이는 추가물은 허브 첫 화면의 버튼 하나뿐이다. 새 디자인 언어를 들이지 않고 기존 카드 배지와 같은 알약 모양·색 체계를 재사용한다. 게임 화면 안쪽은 손대지 않는다.

#### 4.7.1. 허브 상태 버튼

`index.html`의 `.launcher header` 오른쪽 빈 공간에 놓는다. 제목 줄과 같은 높이.

```
로그인 전                          로그인 후
┌────────────────────────────┐    ┌────────────────────────────┐
│ game_ghost      ┌────────┐ │    │ game_ghost      ┌────────┐ │
│ 미니 게임·앱 모음 │ ☁ 저장 │ │    │ 미니 게임·앱 모음 │ ● 동기화됨│ │
│                 └────────┘ │    │                 └────────┘ │
│ 게임 6                     │    │ 게임 6                     │
│ ┌──────┐ ┌──────┐ ┌──────┐│    │ ┌──────┐ ┌──────┐ ┌──────┐│
│ │테트리스│ │스도쿠 │ │로또  ││    │ │테트리스│ │스도쿠 │ │로또  ││
```

로그인 후에는 구글 계정 프로필 사진(원형)과 상태 글자를 표시한다. 표시 상태는 네 가지로 고정한다.

- 동기화됨 (시간 경과 시 "3분 전 저장됨")
- 올리는 중
- 오프라인 (자동 재시도 예정)
- 저장 실패 (누르면 사유 표시)

#### 4.7.2. 계정 메뉴 (프로필 클릭)

지금 저장하기 / 불러오기 / 내보내기(파일 백업) / 로그아웃. **"로그아웃해도 이 기기 기록은 남습니다" 안내 한 줄을 반드시 함께 둔다** - 없으면 사용자가 눌러도 되는지 판단할 수 없다(4.3.6과 짝).

#### 4.7.3. 충돌 선택 대화상자

자동 판정이 불가능할 때(4.3.4)만 뜬다. `shared/ui.js`의 기존 `showModal()`을 쓴다. 새 모달 컴포넌트를 만들지 않는다.

```
┌──────────────────────────────────────┐
│  기록이 서로 다릅니다                  │
│                                      │
│  테트리스                             │
│   ○ 이 기기   최고 12,000 · 5분 전     │
│   ○ 클라우드  최고  9,400 · 어제       │
│                                      │
│  비행슈팅                             │
│   ○ 이 기기   3스테이지 · 어제         │
│   ○ 클라우드  7스테이지 · 10분 전      │
│                                      │
│         [ 취소 ]   [ 선택대로 진행 ]   │
└──────────────────────────────────────┘
```

- 4.7.3.1. **게임마다 개별 선택**이어야 한다. "전부 이 기기" 같은 통짜 선택만 제공하면 한쪽 게임 진행이 통째로 사라진다.
- 4.7.3.2. 각 항목에 **사람이 알아보는 요약**(최고점수·스테이지·진도)을 시각과 함께 표시한다. 시각만 보여주면 무엇을 버리는지 모르는 채 고르게 된다. 요약 문구는 게임별로 다르므로, 게임마다 "요약 만드는 함수"를 하나씩 등록하는 방식으로 둔다(등록 없으면 시각만 표시).

#### 4.7.4. 게임 화면

변화 없음. 업로드 상태를 게임 화면에 표시하지 않고, 게임 도중 로그인 창을 띄우지 않는다. 예외는 저장이 반복 실패할 때의 알림 1회이고 이때도 `shared/ui.js`의 기존 `showToast()`를 쓴다.

#### 4.7.5. 미로그인 사용자

버튼을 무시하면 변경 전과 완전히 동일하다. 로그인 유도 팝업·배너를 만들지 않는다.

## 5. 검증 계획

원칙: **"통과했다"고 말할 때 그 범위를 항상 명시한다.** 형식 검증인지, 가짜 저장소 검증인지, 실제 계정으로 밟은 것인지 구분해 보고한다. 아래 5.2~5.5는 뒤로 갈수록 실제에 가깝고 자동화가 어렵다.

### 5.1. 신규 테스트 파일 배치

| 파일 | 종류 | 실행 |
|---|---|---|
| `tests/cloud-merge.test.mjs` | 순수 로직 단위 검사 | `node tests/cloud-merge.test.mjs` |
| `tests/cloud-sync.test.mjs` | 가짜 저장소 통합 검사 | `node tests/cloud-sync.test.mjs` |
| `tests/smoke.mjs` (기존에 추가) | 정적 규약 검사 | `node tests/smoke.mjs` |

기존 `tests/smoke.mjs`가 외부 의존 0의 순수 node 방식이므로 같은 방식을 따른다. 새 테스트 러너·라이브러리를 도입하지 않는다.

### 5.2. 1층 - 순수 로직 자동 검사 (`cloud-merge.test.mjs`)

네트워크·브라우저·계정 없이 전부 돈다. 데이터 유실 사고는 거의 전부 여기서 잡힌다.

- 5.2.1. 로컬에만 있는 슬롯 → 로컬 채택, 업로드 대상에 포함.
- 5.2.2. 클라우드에만 있는 슬롯 → 클라우드 채택, 로컬에 기록.
- 5.2.3. 양쪽 존재, 클라우드가 최신 → 클라우드 채택.
- 5.2.4. 양쪽 존재, 로컬이 최신 → 로컬 채택.
- 5.2.5. 시각 동일 + 내용 동일 → 아무것도 하지 않음(불필요한 업로드 0).
- 5.2.6. 시각 동일 + 내용 상이 → 자동 판정 금지, "사용자에게 물어야 함" 신호 반환.
- 5.2.7. 로컬 시각이 클라우드보다 미래(기기 시계 오류) → 자동 덮어쓰기 금지, 사용자 확인 신호.
- 5.2.8. **혼합 방향 병합**: 슬롯 A는 로컬이 최신, 슬롯 B는 클라우드가 최신 → 두 슬롯이 각각 올바른 쪽을 채택하고 어느 쪽도 유실되지 않음. (이 케이스가 무너지면 기기 두 대 쓰는 사용자가 데이터를 잃는다)
- 5.2.9. 제외 목록(4.6) 키가 업로드 문서에 포함되지 않음.
- 5.2.10. 형식 버전이 미래 값(`schema: 99`)인 문서 → 해석 시도 금지, 로컬 유지 + 업로드 중단.
- 5.2.11. 손상된 JSON / 슬롯이 객체가 아님 / `updatedAt` 누락 → 예외로 죽지 않고 로컬 유지.
- 5.2.12. 문서 크기 상한 초과 → 업로드 거부 + 알림 신호(조용한 실패 0).
- 5.2.13. 병합 함수가 입력 객체를 변형하지 않음(원본 불변).

### 5.3. 2층 - 가짜 저장소 통합 검사 (`cloud-sync.test.mjs`)

진짜 구글 대신 메모리 위에서 도는 가짜 드라이브와 가짜 로그인을 끼운다. 조립부가 순서대로 움직이는지를 본다.

- 5.3.1. 미로그인 상태에서 게임이 저장 → 기기 저장은 정상, 업로드 시도 0. (미로그인 사용자에게 기존과 다른 동작이 생기면 안 된다)
- 5.3.2. 로그인 → 클라우드 비어 있음 → 로컬 전체가 1회 업로드됨.
- 5.3.3. 로그인 → 클라우드에 기록 있음 → 로컬에 반영되고, 게임이 다시 읽었을 때 반영된 값이 나옴.
- 5.3.4. 업로드 실패(가짜 저장소가 오류 반환) → 게임 저장은 성공한 채로 남고, 다음 저장 때 재시도됨. 사용자에게 실패 상태가 보임.
- 5.3.5. 연속 저장 10회 → 업로드는 디바운스로 1~2회. (요청 폭주 방지)
- 5.3.6. 로그아웃 → 로컬 데이터 잔존 확인(4.3.6).
- 5.3.7. 토큰 만료 후 조용한 재발급 실패 → 동기화 비활성, 게임 진행에는 영향 0(4.4.4).
- 5.3.8. 서비스워커 정책 정적 확인: `service-worker.js`가 외부 출처 요청을 통과시키는 분기(3.3)를 유지하는지 `tests/smoke.mjs`에서 검사. 이 분기가 사라지면 로그인이 깨진다.
- 5.3.9. 권한 문자열 정적 확인: 소스 전체에 `drive.appdata` 외의 드라이브 권한이 등장하면 실패(2.5 불변 조건 자동 강제).

### 5.4. 3층 - 실화면 검증 (browser-shot)

로컬 dev 서버에서 실제 브라우저로 연다. 로그인은 가짜 모드(`?cloudmock=1`)로 대체해 사람 없이 화면까지 확인한다.

- 5.4.1. 허브 진입 - 로그인 버튼이 실제로 보이는지(`display`/`visibility`/`offsetParent` 확인), 콘솔 에러 0.
- 5.4.2. 가짜 로그인 후 - 상태 표시가 "동기화됨 + 시각"으로 바뀌는지. **크리에이터가 넣은 값이 화면에 실제로 나오는지 대조**(글로벌 3.9의 유령 출력 검사).
- 5.4.3. 게임 7종 + lotto 각각 진입해 콘솔 에러 0 (저장 창구를 건드렸으므로 전 게임이 회귀 대상이다. 표본 검사 금지, 8종 전수).
- 5.4.4. 충돌 확인 대화상자(4.3.4)가 실제로 뜨고 두 선택지가 각각 동작하는지.

### 5.5. 4층 - 실계정 수동 체크리스트 (사람만 가능)

자동화가 불가능한 영역. 구현 완료 후 자비스가 순서를 안내하고 결과를 문서에 기록한다. **이 목록을 다 밟기 전에는 "됐다"고 보고하지 않는다.**

- 5.5.1. 실제 구글 계정으로 로그인 → 로그인 창에 경고 화면이 뜨지 않는지 확인(2.3 검증).
- 5.5.2. PC에서 진행 → 폰에서 로그인 → 진행이 복원되는지.
- 5.5.3. 시크릿 창(완전 초기 상태)에서 로그인 → 복원되는지.
- 5.5.4. 로그인 창을 취소·거부 → 게임이 평소대로 동작하는지.
- 5.5.5. 팝업 차단이 켜진 브라우저에서의 동작.
- 5.5.6. iOS 사파리에서 1회 확인(사파리는 기기 저장을 주기적으로 비우므로 이 기능의 최대 수혜 대상이자 취약 지점).
- 5.5.7. 1시간 이상 방치 후 저장 → 조용한 재발급이 되는지(4.4.2).
- 5.5.8. 다른 구글 계정으로 갈아타기 → 앞 계정 데이터가 섞이지 않는지.
- 5.5.9. 두 기기에서 동시에 다른 게임 진행 → 둘 다 살아남는지(5.2.8의 실환경 확인).
- 5.5.10. 구글 계정 설정에서 이 사이트 연결 해제 → 다음 방문 시 오류 없이 미로그인 상태로 돌아가는지.

### 5.6. 배포 파이프라인 편입

5.6.1. `.claude/deploy.json`의 `test.command`에 `node tests/cloud-merge.test.mjs`, `node tests/cloud-sync.test.mjs`, `node tests/smoke.mjs`를 추가한다. 이후 모든 배포에서 자동 실행된다.

5.6.2. `smoke.urls`는 현재 허브와 english-reading 2개뿐이다. 저장 창구를 건드리는 변경이므로 배포 후 스모크 대상에 게임 페이지를 추가한다(콘솔 에러 예산 0 유지).

5.6.3. 서비스워커 캐시 번호를 올린다(현재 v194). `shared/storage.js`가 바뀌는데 캐시가 갱신 안 되면 사용자에게 옛 코드가 계속 나간다.

### 5.7. 기존 사용자 회귀 방지 (최우선)

이번 변경의 가장 큰 위험은 새 기능 실패가 아니라 **이미 놀던 사람의 데이터가 깨지는 것**이다.

- 5.7.1. 미로그인 사용자의 동작이 변경 전과 완전히 동일함을 5.3.1 + 5.4.3으로 확인.
- 5.7.2. 변경 전 브라우저에 저장된 데이터를 백업해 두고, 변경 후 그대로 읽히는지 대조.
- 5.7.3. **동기화 누락 키 0 검사**: 게임을 실제로 한 판씩 돌린 뒤 브라우저에 남은 저장 키 전부를 훑어, 업로드 문서에 담기지 않은 키가 있으면 실패로 본다. 제외 목록(4.6)에 명시된 것만 예외로 인정한다. 선언한 것과 실제 저장하는 것이 어긋나는 사고(글로벌 3.9 죽은 입력 대조)를 여기서 잡는다.
- 5.7.4. 되돌리기 경로: 문제가 생기면 `shared/storage.js`의 동기화 알림 한 줄만 꺼도 기존 동작으로 즉시 복귀하도록 설계한다. 되돌리기가 커밋 되돌리기 없이 가능해야 한다.

## 6. 구현 순서 (승인 후)

6.1. 순수 로직(`merge.js`) + 1층 테스트를 **먼저** 만든다. 구글 연결 없이 여기까지 완주한다.

6.2. 가짜 저장소 + 조립부(`sync.js`) + 2층 테스트.

6.3. `shared/storage.js` 내부 편입(게임 코드 수정 0) → 5.4.3 전수 회귀 확인.

6.4. lotto 어댑터(함수 2개) → lotto 회귀 테스트.

6.5. 구글 로그인 연결(`auth.js`) + 허브 버튼. 이 시점에 사용자께 콘솔 등록번호 발급을 요청한다.

6.6. 실계정 체크리스트 5.5 수행.

6.7. 배포 파이프라인 편입(5.6) 후 배포.

## 7. 리스크와 미결

7.1. **페이지 이동마다 토큰 재확보**(4.4.4). 이 설계의 가장 약한 지점. 실계정 확인 전까지는 되는지 단정할 수 없다.

7.2. **구글 콘솔 화면·정책 변동**. 게시 전환 단계에서 콘솔이 추가 요구를 걸 가능성은 남아 있다. 그 시점에 사용자께 보고한다.

7.3. **동시 편집 완전 해결 아님**. 두 기기에서 같은 게임을 동시에 진행하면 한쪽 진행은 사용자 선택으로 버려진다. 서버 없이 이보다 정교하게 만들려면 비용이 급증하므로, 현 단계에서는 "묻고 고르게 한다"까지가 상한이다.

7.4. **미결**: 로그인 버튼을 허브에만 둘지, 게임 화면 상단에도 노출할지. 4.5.3은 허브 전용으로 잡았으나 게임에서 바로 로그인하고 싶다는 요구가 나올 수 있다. 구현 6.5 시점에 재검토.

## 8. 사용자에게 부탁드릴 작업 (구현 6.5 단계, 1회)

구글 클라우드 콘솔에서 등록번호를 발급받는 절차. 계정 소유자만 할 수 있어 자비스가 대행할 수 없다. 화면 클릭 순서는 그 시점에 하나씩 안내한다. 콘솔 조작 외에 명령어 입력은 요구하지 않는다(글로벌 2.6 / 허브 6.4).

- 8.1. 프로젝트 생성.
- 8.2. 로그인 동의 화면 설정(외부 / 앱 이름 / 연락 메일).
- 8.3. 사용자 인증 정보에서 **웹 애플리케이션** 유형으로 등록번호 발급.
- 8.4. 허용 주소에 `https://ghostjean-hash.github.io`(배포용)와 `http://127.0.0.1:8000`(개발용) 등록.
- 8.5. 게시 상태를 "게시"로 전환(2.4).
- 8.6. 발급된 등록번호를 자비스에게 전달. 비밀키는 쓰지 않으므로 공개 저장소에 그대로 넣어도 안전하다.
