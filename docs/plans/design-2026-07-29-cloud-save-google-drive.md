# 구글 드라이브 세이브 동기화 설계 (계획, 구현 착수 전)

> 작성 2026-07-29. 상태: **승인됨(2026-07-29 사용자 결정) · S1~S4 완료, 다음은 S5(구글 연결)**. 진행 기록은 9장.
> 단일 진실 source (글로벌 CLAUDE.md 6.5). 구현 중 설계가 바뀌면 코드보다 이 문서를 먼저 고친다.

변경 영향 범위: **H** (전 게임·앱 7종의 저장 창구를 건드리고, 실패 시 기존 사용자 진행 데이터가 유실될 수 있다).

## 1. 목적과 범위

1.1. 목적: 기기·브라우저를 바꿔도 게임/앱 진행이 유지되게 한다. 서버는 운영하지 않는다.

1.2. 방식: 사용자가 자기 구글 계정으로 로그인하면, 그 사람 드라이브 안의 **이 웹사이트 전용 숨김 폴더**에 세이브가 저장된다. 데이터 소유자는 사용자 본인이고, 우리는 저장소를 갖지 않는다.

1.3. 사용자 확정 전제 (2026-07-29 대화)
- 1.3.1. 불특정 다수 공개. 사이트 방문자 누구나 로그인해 쓸 수 있어야 한다.
- 1.3.2. 서버 운영 금지. GitHub Pages 정적 호스팅 유지.
- 1.3.3. 저장 위치는 사용자 본인 드라이브.

1.4. 범위에 포함: 등록된 게임 6종(tetris / sudoku / lotto / rushhour / nonogram / flightshooting) + 앱 2종(english-reading / english-vocabulary)의 진행 데이터.

1.5. 범위 밖: 계정 간 데이터 공유, 순위표, 서버 검증, 결제. 지금 설계는 "내 데이터를 내 계정에 붙여둔다"까지다.

## 2. 권한 등급과 심사 (확인 완료)

2.1. 사용할 권한은 `drive.appdata` 하나. 이 웹사이트가 만든 숨김 폴더만 읽고 쓴다. 사용자의 기존 드라이브 파일은 목록조차 못 본다.

2.2. 구글 분류상 **민감하지 않은 권한(non-sensitive)** 이다. 민감하지 않은 권한만 쓰는 앱은 검증 절차 완료 의무가 없다 (출처: [Choose Google Drive API scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [OAuth App Verification Help Center](https://support.google.com/cloud/answer/13463073?hl=en)).

2.3. "확인되지 않은 앱" 경고는 민감·제한 권한을 심사 전에 요청할 때 뜬다. 우리 조합에서는 뜨지 않는다 (출처: [Unverified apps](https://support.google.com/cloud/answer/7454865?hl=en)).

2.4. 100명 제한은 심사가 아니라 콘솔 게시 상태가 "테스트 중"일 때 걸린다. "게시" 상태로 전환하면 풀린다.

2.5. **설계 불변 조건**: 권한을 `drive.appdata` 하나로 고정한다. `drive`(전체 접근)를 쓰는 순간 최고 등급인 "제한됨"이 되어 매년 외부 보안 감사가 붙는다. 코드 리뷰에서 이 권한 문자열이 늘어나면 즉시 반려한다.

2.6. 선택 사항: 로그인 창에 사이트 이름·로고를 띄우려면 "브랜드 확인"이라는 가벼운 별도 절차가 필요하다. 안 하면 주소만 표시된다. 동작에는 무관하므로 후순위.

## 3. 현재 상태 진단

3.1. **저장 창구가 이미 통일돼 있다.** tetris / sudoku / rushhour / nonogram / flightshooting / english-reading / english-vocabulary 7종이 전부 `shared/storage.js`의 `createStorage(네임스페이스)`만 거치고, 실제 키는 `gg.<네임스페이스>.*`로 자동 접두된다. 즉 파일 한 곳의 안쪽만 바꾸면 7종이 한꺼번에 편입된다.

3.2. **예외는 lotto 하나.** `games/lotto/src/data/storage.js`가 자체 접두 `lotto_`로 직접 읽고 쓴다. 다만 이 파일 안의 `read()` / `write()` 두 함수가 유일한 통로이고 "core에서 직접 접근 금지" 규율이 지켜지고 있어, 이 두 함수만 갈아끼우면 된다.

3.3. **서비스워커는 외부 요청을 안 건드린다.** `service-worker.js:199`가 `url.origin !== self.location.origin`이면 즉시 통과시킨다. 구글 로그인 스크립트와 드라이브 통신은 캐시 간섭을 받지 않는다. 다만 이건 현재 코드가 그렇다는 것이고, 검증 항목으로 남긴다(5.3.6).

3.4. **검증 인프라가 이미 있다.** `tests/smoke.mjs`(허브 정적 스모크, 순수 node), 앱별 `run-node` 테스트, `.claude/deploy.json`의 배포 파이프라인(테스트 → push → 실제 URL 스모크, 콘솔 에러 예산 0), `browser-shot` skill(실화면·콘솔 검사). 새 검증은 이 위에 얹는다.

## 4. 설계

### 4.1. 계층 분리 (검증 가능성이 설계를 결정한다)

구글 로그인은 사람이 버튼을 눌러야 해서 자동 테스트가 불가능하다. 그래서 **자동으로 검증할 수 있는 것을 최대한 많이 남기도록** 세 층으로 자른다.

| 층 | 파일(예정) | 하는 일 | 자동 검증 |
|---|---|---|---|
| 순수 로직 | `shared/cloud/merge.js` | 어느 쪽이 최신인지 판정, 세이브 묶음 병합, 형식 검사 | **100% 가능** (네트워크·브라우저 0) |
| 저장소 어댑터 | `shared/cloud/remote.js` | 세이브 문서를 올리고 내린다 | 가짜 저장소로 **가능** |
| 로그인 | `shared/cloud/auth.js` | 구글 로그인 창, 접속 토큰 관리 | 불가 (사람 체크리스트) |
| 조립 | `shared/cloud/sync.js` | 위 셋을 엮어 실제 동기화 수행 | 가짜 저장소 + 가짜 로그인으로 **가능** |

핵심: `merge.js`에는 `window`도 `fetch`도 등장하지 않는다. 순수 함수만 둔다. 데이터가 깨지는 사고는 거의 전부 이 층에서 나므로, 위험이 큰 부분을 자동 검증 100% 영역에 몰아넣는 것이 이 분리의 목적이다.

### 4.2. 세이브 문서 형식

드라이브 숨김 폴더에 파일 하나(`save-v1.json`)만 둔다. 게임마다 파일을 나누지 않는 이유는 요청 횟수와 충돌 지점을 줄이기 위해서다.

```
{
  "schema": 1,                       // 형식 버전. 올라가면 마이그레이션 경유
  "updatedAt": 1753747200000,        // 문서 전체 최종 갱신(참고용)
  "device": "chrome-win-9f2a",       // 어느 기기가 마지막에 썼는지(디버깅용)
  "slots": {
    "gg.tetris":        { "updatedAt": 1753740000000, "data": { "highscore": 12000 } },
    "gg.flightshooting":{ "updatedAt": 1753747200000, "data": { ... } },
    "lotto":            { "updatedAt": 1753700000000, "data": { ... } }
  }
}
```

4.2.1. **슬롯 = 게임 하나**. 게임별로 최종 갱신 시각을 따로 갖는다. 이게 있어야 "테트리스는 PC가 최신, 비행슈팅은 폰이 최신"인 상황에서 둘 다 살아남는다.

4.2.2. 슬롯 안의 `data`는 그 게임이 저장하던 키/값을 그대로 담는다. 게임 코드는 자기 데이터 모양을 바꾸지 않는다.

4.2.3. 문서 총량 상한을 둔다(예: 1MB). 넘으면 업로드를 중단하고 사용자에게 알린다. 조용한 실패 금지.

### 4.3. 동기화 규칙

4.3.1. **로컬 우선**. 게임은 지금처럼 기기 저장에 즉시 쓴다. 클라우드는 그 뒤를 따라간다. 네트워크가 끊겨도 게임은 평소대로 동작한다.

4.3.2. **올리기**: 저장이 발생하면 곧바로 올리지 않고 몇 초 모았다가(디바운스) 한 번에 올린다. 페이지를 떠날 때도 한 번 밀어낸다.

4.3.3. **내리기**: 로그인 직후, 그리고 페이지 진입 시 1회.

4.3.4. **충돌 판정** (슬롯 단위, 순수 함수)
- 한쪽에만 있으면 있는 쪽을 쓴다.
- 양쪽에 있고 시각이 다르면 최신을 쓴다.
- 시각이 같고 내용이 같으면 그대로 둔다.
- 시각이 같은데 내용이 다르면 **자동으로 덮지 않는다**. 사용자에게 "이 기기 기록 / 클라우드 기록" 중 선택을 묻는다.
- 어느 쪽이든 저장 시각이 **현재 시각보다 크게 미래**면(기기 시계 오류) 그 시각을 믿을 수 없으므로 자동 판정을 포기하고 사용자에게 묻는다. 기준은 현재 시각이지 상대 쪽 시각이 아니다 - 로컬이 클라우드보다 나중인 것은 오래 접속하지 않은 정상 상황이다.

4.3.5. **첫 로그인**: 이미 이 기기에서 놀던 사람이 처음 로그인하면 로컬 기록이 있고 클라우드는 비어 있다. 이때는 로컬을 올린다. 반대로 클라우드에만 있으면 내린다. 양쪽 다 있으면 4.3.4를 슬롯마다 적용한다.

4.3.6. **로그아웃 시 로컬 데이터를 지우지 않는다.** 지우면 사용자가 진행을 잃는다.

### 4.4. 로그인과 토큰

4.4.1. 구글이 웹페이지용으로 제공하는 로그인 라이브러리를 `<script>` 한 줄로 불러온다. 빌드 도구·설치 없음.

4.4.2. 접속 토큰의 수명은 약 1시간이고 갱신 토큰은 브라우저 방식에서 발급되지 않는다. **2026-08-01 전면 개정** - 이전 규정("구글 부품에게 창을 띄우지 않는 조용한 재발급을 맡기고 만료 5분 전에 미리 갱신한다")은 전제가 틀렸다. 그 부품은 요청에서 prompt를 비워도 실제로는 팝업 창을 열고 즉시 닫으므로, 팝업 차단을 켠 사용자에게는 갱신이 통째로 실패했고 그 외 사용자에게는 창이 번쩍였다. 예약 갱신 타이머는 폐기하고, 만료 후 되살리기는 4.4.6의 주소 이동 방식으로 옮긴다.

4.4.3. 토큰 보관 위치: **`localStorage`**(2026-07-31 변경, 이전 규정은 `sessionStorage` 전용).

- 4.4.3.1. 변경 이유. `sessionStorage`는 탭·창을 닫으면 사라진다. 그래서 재방문마다 재발급이 필요하고, 조용한 재발급은 구글 세션 쿠키에 의존하므로 홈 화면 실행(PWA)·쿠키 제한 브라우저에서 자주 실패한다. 결과가 잦은 로그인 요구였다(사용자 보고 2026-07-31).
- 4.4.3.2. 트레이드오프. 접속 토큰이 기기에 남으므로 스크립트 주입 사고 시 노출될 수 있다. 다만 권한이 `drive.appdata` 하나뿐이어서(2.5 불변 조건) 피해 범위는 이 사이트 전용 숨김 폴더로 한정되고, 수명 1시간 상한도 그대로다. 로그인 유지와 이 노출 범위를 맞바꾼 판단이다(사용자 승인 2026-07-31).
- 4.4.3.3. 이전 방식으로 보관된 토큰은 첫 접근 시 새 위치로 옮긴다. 이미 로그인해 둔 사용자가 다시 로그인하지 않게 한다(5.7 회귀 방지).
- 4.4.3.4. 여러 페이지가 동시에 열려 있으면 한쪽이 갱신한 토큰을 다른 쪽이 그대로 쓴다. 메모리에 유효한 토큰이 없을 때 보관 위치를 다시 읽어 확인한다.

4.4.4. **각 게임이 별도 페이지라는 점이 이 설계의 최대 난점이다.** 허브에서 게임으로 이동하면 문서가 새로 뜨므로 토큰을 다시 얻어야 한다. 같은 출처라 보관 위치는 공유되지만 만료 시점이 게임 도중에 올 수 있다. 대응: 게임 진입 시 조용한 재발급을 시도하고, 실패하면 **동기화만 끄고 게임은 그대로 진행**시킨다. 게임 중간에 로그인 창을 띄우지 않는다. 이 항목은 5.5의 실계정 체크리스트에서 반드시 확인한다.

4.4.5. **드라이브가 "유효기간 지남"으로 거절해도 로그인 창을 띄우지 않는다**(2026-07-31 신설). 거절 응답을 받으면 갖고 있던 토큰을 버리고 조용한 재발급만 한 번 시도한다. 그것도 실패하면 동기화만 멈추고(`disabled`) 사용자가 허브 버튼을 직접 누를 때까지 기다린다. 자동 저장은 게임 화면에서도 돌기 때문에(9.3) 이 통로가 창을 띄우면 4.4.4 규정이 무의미해진다.

4.4.6. **주소 이동 방식 갱신**(2026-08-01 신설, 사용자 결정). 사용자 신고 둘 - 팝업이 2번 뜬다, 팝업을 막으면 아예 안 뜬다, 1시간마다 로그인이 풀린다. 원인 셋을 아래 세 항목으로 나누어 처방한다. 갱신용 열쇠는 서버 없이 받을 수 없다는 한계는 그대로이고(7.1 유지), 대신 구글 자체 로그인 세션(보통 몇 달 유지)을 매번 새 출입증으로 바꿔 오는 방식으로 우회한다.

- 4.4.6.1. **되살리기는 팝업이 아니라 같은 창의 주소 이동으로 한다.** 허브에 들어올 때 유효한 출입증이 없고 이 기기에 로그인 이력이 있으면, `accounts.google.com/o/oauth2/v2/auth`에 `response_type=token` + `prompt=none`으로 이동해 새 출입증을 받아 돌아온다. 팝업이 아니므로 차단 설정과 무관하다. 발동 조건이 하나라도 어긋나면 아무 일도 하지 않는다 - (a) `config.js`의 스위치가 켜져 있어야 한다, (b) **현재 주소가 콘솔에 등록한 주소와 글자 하나까지 같아야 한다**(다르면 사용자가 구글의 400 오류 화면에 갇힌다. 2026-08-01 실측 확인), (c) 홈 화면에 추가한 앱(아이폰)에서는 하지 않는다(바깥 주소로 나가면 돌아오지 못할 수 있다), (d) 창 안의 창에서는 하지 않는다, (e) 한 브라우저 세션에 한 번만, (f) 실패했으면 30분간 쉰다. (e)+(f)가 되돌이 방지의 이중 장치다. 게임 화면은 (b)에서 자동으로 걸러진다 - 놀이 중인 판을 날리지 않는다(4.4.4와 같은 이유).
- 4.4.6.2. **돌아온 결과는 주소의 `#` 뒤에서 받는다.** 보낼 때 남긴 대조값(`state`)이 일치할 때만 처리하고, 아니면 남의 주소로 보아 손대지 않는다. 성공하면 출입증을 보관소로 옮기고 억제 기록을 지운다(다음 만료 때 다시 다녀올 수 있게). 실패(`error=login_required` 등)하면 억제 시각만 남긴다. 어느 쪽이든 주소창에서 우리가 붙인 값만 걷어내고 `?cloudmock=1` 같은 다른 값은 남긴다.
- 4.4.6.3. **조용한 경로에서는 어떤 경우에도 창을 열지 않는다.** 창은 사용자가 버튼을 직접 누른 순간에만 뜬다(첫 로그인, 그리고 동기화가 멈춘 상태에서 "다시 로그인"을 누를 때). 사용자 조작이 없는 시점에 여는 창은 팝업 차단에 막히므로 애초에 시도하지 않는다.
- 4.4.6.4. **같은 순간의 중복 요청은 하나로 묶는다.** 이전 구현은 진행 중인 요청을 공유하지 않아 두 곳이 동시에 출입증을 달라고 하면 창이 두 개 열렸다(신고된 "2번 뜬다"의 유력 원인). 요청이 끝나면 잠금을 풀어 다음 요청은 정상 진행한다. 다만 첫 로그인에서 구글이 계정 선택과 권한 동의를 연달아 보여 주는 것은 구글의 정상 흐름이고 바꿀 수 없다.
- 4.4.6.5. **콘솔 등록이 전제다.** 스위치를 켜기 전에 구글 클라우드 콘솔의 "승인된 리디렉션 URI"에 배포 주소를 등록해야 한다. 등록 없이 켜면 사용자가 오류 화면에 갇히므로 기본값은 꺼짐이고, 등록 확인 후에만 켠다.

### 4.5. 게임 편입 방식

4.5.1. `shared/storage.js`의 `createStorage()`는 **호출부 시그니처를 바꾸지 않는다**. 내부에서만 "저장할 때 동기화 큐에 알린다"를 추가한다. 따라서 게임 7종은 코드 수정 0.

4.5.2. lotto만 `games/lotto/src/data/storage.js`의 `read()` / `write()`에 같은 처리를 넣는다. 함수 2개.

4.5.3. 허브 `index.html`에 로그인 버튼과 상태 표시(마지막 동기화 시각)를 넣는다. 게임 화면 안에는 버튼을 넣지 않는다.

### 4.6. 동기화 제외 목록

용량이 크고 언제든 다시 받을 수 있는 데이터는 올리지 않는다. 진행 기록이 아니라 캐시이기 때문이다.

- `lotto_draws` (회차 전체 캐시. 원본을 다시 페치하면 복원된다)
- `lotto_stats_*` (draws에서 재계산되는 파생값)
- 서비스워커 캐시 일체

제외 목록은 코드에 상수로 두고, 5.2.9 테스트로 "제외 대상이 문서에 섞여 들어가지 않음"을 검사한다.

### 4.7. 화면 설계

원칙: 눈에 보이는 추가물은 허브 첫 화면의 버튼 하나뿐이다. 새 디자인 언어를 들이지 않고 기존 카드 배지와 같은 알약 모양·색 체계를 재사용한다. 게임 화면 안쪽은 손대지 않는다.

#### 4.7.1. 허브 상태 버튼

`index.html`의 `.launcher header` 오른쪽 빈 공간에 놓는다. 제목 줄과 같은 높이.

```
로그인 전                          로그인 후
┌────────────────────────────┐    ┌────────────────────────────┐
│ game_ghost      ┌────────┐ │    │ game_ghost      ┌────────┐ │
│ 미니 게임·앱 모음 │ ☁ 저장 │ │    │ 미니 게임·앱 모음 │ ● 동기화됨│ │
│                 └────────┘ │    │                 └────────┘ │
│ 게임 6                     │    │ 게임 6                     │
│ ┌──────┐ ┌──────┐ ┌──────┐│    │ ┌──────┐ ┌──────┐ ┌──────┐│
│ │테트리스│ │스도쿠 │ │로또  ││    │ │테트리스│ │스도쿠 │ │로또  ││
```

로그인 후에는 구글 계정 프로필 사진(원형)과 상태 글자를 표시한다. 표시 상태는 네 가지로 고정한다.

- 동기화됨 (시간 경과 시 "3분 전 저장됨")
- 올리는 중
- 오프라인 (자동 재시도 예정)
- 저장 실패 (누르면 사유 표시)

#### 4.7.2. 계정 메뉴 (프로필 클릭)

지금 저장하기 / 클라우드에서 불러오기 / 파일로 내보내기 / 로그아웃 / 닫기. 세로로 쌓는다(가로 배치는 항목이 셋만 넘어도 찌그러진다).

**설명 문장을 넣지 않는다(사용자 지시 2026-07-29).** 처음에는 "로그아웃해도 이 기기 기록은 남습니다" 안내를 의무로 적었으나 사용자가 제거를 지시했다. 메뉴에는 선택지 라벨만 둔다. 뜻이 모호하면 문장을 덧붙이는 대신 라벨을 고친다("불러오기" → "클라우드에서 불러오기"). 전 도메인 공통 규칙 후보로 글로벌에 인계했다.

#### 4.7.3. 충돌 선택 대화상자

자동 판정이 불가능할 때(4.3.4)만 뜬다. `shared/ui.js`의 기존 `showModal()`을 쓴다. 새 모달 컴포넌트를 만들지 않는다.

```
┌──────────────────────────────────────┐
│  기록이 서로 다릅니다                  │
│                                      │
│  테트리스                             │
│   ○ 이 기기   최고 12,000 · 5분 전     │
│   ○ 클라우드  최고  9,400 · 어제       │
│                                      │
│  비행슈팅                             │
│   ○ 이 기기   3스테이지 · 어제         │
│   ○ 클라우드  7스테이지 · 10분 전      │
│                                      │
│         [ 취소 ]   [ 선택대로 진행 ]   │
└──────────────────────────────────────┘
```

- 4.7.3.1. **게임마다 개별 선택**이어야 한다. "전부 이 기기" 같은 통짜 선택만 제공하면 한쪽 게임 진행이 통째로 사라진다.
- 4.7.3.2. 각 항목에 **사람이 알아보는 요약**(최고점수·스테이지·진도)을 시각과 함께 표시한다. 시각만 보여주면 무엇을 버리는지 모르는 채 고르게 된다. 요약 문구는 게임별로 다르므로, 게임마다 "요약 만드는 함수"를 하나씩 등록하는 방식으로 둔다(등록 없으면 시각만 표시).

#### 4.7.4. 게임 화면

변화 없음. 업로드 상태를 게임 화면에 표시하지 않고, 게임 도중 로그인 창을 띄우지 않는다. 예외는 저장이 반복 실패할 때의 알림 1회이고 이때도 `shared/ui.js`의 기존 `showToast()`를 쓴다.

#### 4.7.5. 미로그인 사용자

버튼을 무시하면 변경 전과 완전히 동일하다. 로그인 유도 팝업·배너를 만들지 않는다.

## 5. 검증 계획

원칙: **"통과했다"고 말할 때 그 범위를 항상 명시한다.** 형식 검증인지, 가짜 저장소 검증인지, 실제 계정으로 밟은 것인지 구분해 보고한다. 아래 5.2~5.5는 뒤로 갈수록 실제에 가깝고 자동화가 어렵다.

### 5.1. 신규 테스트 파일 배치

| 파일 | 종류 | 실행 |
|---|---|---|
| `tests/cloud-merge.test.mjs` | 순수 로직 단위 검사 | `node tests/cloud-merge.test.mjs` |
| `tests/cloud-sync.test.mjs` | 가짜 저장소 통합 검사 | `node tests/cloud-sync.test.mjs` |
| `tests/smoke.mjs` (기존에 추가) | 정적 규약 검사 | `node tests/smoke.mjs` |

기존 `tests/smoke.mjs`가 외부 의존 0의 순수 node 방식이므로 같은 방식을 따른다. 새 테스트 러너·라이브러리를 도입하지 않는다.

### 5.2. 1층 - 순수 로직 자동 검사 (`cloud-merge.test.mjs`)

네트워크·브라우저·계정 없이 전부 돈다. 데이터 유실 사고는 거의 전부 여기서 잡힌다.

- 5.2.1. 로컬에만 있는 슬롯 → 로컬 채택, 업로드 대상에 포함.
- 5.2.2. 클라우드에만 있는 슬롯 → 클라우드 채택, 로컬에 기록.
- 5.2.3. 양쪽 존재, 클라우드가 최신 → 클라우드 채택.
- 5.2.4. 양쪽 존재, 로컬이 최신 → 로컬 채택.
- 5.2.5. 시각 동일 + 내용 동일 → 아무것도 하지 않음(불필요한 업로드 0).
- 5.2.6. 시각 동일 + 내용 상이 → 자동 판정 금지, "사용자에게 물어야 함" 신호 반환.
- 5.2.7. 로컬 시각이 클라우드보다 미래(기기 시계 오류) → 자동 덮어쓰기 금지, 사용자 확인 신호.
- 5.2.8. **혼합 방향 병합**: 슬롯 A는 로컬이 최신, 슬롯 B는 클라우드가 최신 → 두 슬롯이 각각 올바른 쪽을 채택하고 어느 쪽도 유실되지 않음. (이 케이스가 무너지면 기기 두 대 쓰는 사용자가 데이터를 잃는다)
- 5.2.9. 제외 목록(4.6) 키가 업로드 문서에 포함되지 않음.
- 5.2.10. 형식 버전이 미래 값(`schema: 99`)인 문서 → 해석 시도 금지, 로컬 유지 + 업로드 중단.
- 5.2.11. 손상된 JSON / 슬롯이 객체가 아님 / `updatedAt` 누락 → 예외로 죽지 않고 로컬 유지.
- 5.2.12. 문서 크기 상한 초과 → 업로드 거부 + 알림 신호(조용한 실패 0).
- 5.2.13. 병합 함수가 입력 객체를 변형하지 않음(원본 불변).

### 5.3. 2층 - 가짜 저장소 통합 검사 (`cloud-sync.test.mjs`)

진짜 구글 대신 메모리 위에서 도는 가짜 드라이브와 가짜 로그인을 끼운다. 조립부가 순서대로 움직이는지를 본다.

- 5.3.1. 미로그인 상태에서 게임이 저장 → 기기 저장은 정상, 업로드 시도 0. (미로그인 사용자에게 기존과 다른 동작이 생기면 안 된다)
- 5.3.2. 로그인 → 클라우드 비어 있음 → 로컬 전체가 1회 업로드됨.
- 5.3.3. 로그인 → 클라우드에 기록 있음 → 로컬에 반영되고, 게임이 다시 읽었을 때 반영된 값이 나옴.
- 5.3.4. 업로드 실패(가짜 저장소가 오류 반환) → 게임 저장은 성공한 채로 남고, 다음 저장 때 재시도됨. 사용자에게 실패 상태가 보임.
- 5.3.5. 연속 저장 10회 → 업로드는 디바운스로 1~2회. (요청 폭주 방지)
- 5.3.6. 로그아웃 → 로컬 데이터 잔존 확인(4.3.6).
- 5.3.7. 토큰 만료 후 조용한 재발급 실패 → 동기화 비활성, 게임 진행에는 영향 0(4.4.4).
- 5.3.8. 서비스워커 정책 정적 확인: `service-worker.js`가 외부 출처 요청을 통과시키는 분기(3.3)를 유지하는지 `tests/smoke.mjs`에서 검사. 이 분기가 사라지면 로그인이 깨진다.
- 5.3.9. 권한 문자열 정적 확인: 소스 전체에 `drive.appdata` 외의 드라이브 권한이 등장하면 실패(2.5 불변 조건 자동 강제).

### 5.4. 3층 - 실화면 검증 (browser-shot)

로컬 dev 서버에서 실제 브라우저로 연다. 로그인은 가짜 모드(`?cloudmock=1`)로 대체해 사람 없이 화면까지 확인한다.

- 5.4.1. 허브 진입 - 로그인 버튼이 실제로 보이는지(`display`/`visibility`/`offsetParent` 확인), 콘솔 에러 0.
- 5.4.2. 가짜 로그인 후 - 상태 표시가 "동기화됨 + 시각"으로 바뀌는지. **크리에이터가 넣은 값이 화면에 실제로 나오는지 대조**(글로벌 3.9의 유령 출력 검사).
- 5.4.3. 게임 7종 + lotto 각각 진입해 콘솔 에러 0 (저장 창구를 건드렸으므로 전 게임이 회귀 대상이다. 표본 검사 금지, 8종 전수).
- 5.4.4. 충돌 확인 대화상자(4.3.4)가 실제로 뜨고 두 선택지가 각각 동작하는지.

### 5.5. 4층 - 실계정 수동 체크리스트 (사람만 가능)

자동화가 불가능한 영역. 구현 완료 후 자비스가 순서를 안내하고 결과를 문서에 기록한다. **이 목록을 다 밟기 전에는 "됐다"고 보고하지 않는다.**

- 5.5.1. 실제 구글 계정으로 로그인 → 로그인 창에 경고 화면이 뜨지 않는지 확인(2.3 검증).
- 5.5.2. PC에서 진행 → 폰에서 로그인 → 진행이 복원되는지.
- 5.5.3. 시크릿 창(완전 초기 상태)에서 로그인 → 복원되는지.
- 5.5.4. 로그인 창을 취소·거부 → 게임이 평소대로 동작하는지.
- 5.5.5. 팝업 차단이 켜진 브라우저에서의 동작. (2026-08-01 개정 - 이제 창은 사용자가 버튼을 누를 때만 뜨므로 차단 설정이 갱신을 막지 못해야 한다. 첫 로그인 클릭 시 창이 **한 개만** 뜨는지도 여기서 본다.)
- 5.5.6. iOS 사파리에서 1회 확인(사파리는 기기 저장을 주기적으로 비우므로 이 기능의 최대 수혜 대상이자 취약 지점).
- 5.5.7. 1시간 이상 방치 후 허브 재진입 → 주소 이동 갱신이 화면 깜빡임 한 번으로 끝나고 로그인이 유지되는지(4.4.6). 콘솔에 리디렉션 주소를 등록하고 스위치를 켠 뒤에 확인한다. 홈 화면 앱에서는 발동하지 않는 것이 정상이다(4.4.6.1-c).
- 5.5.8. 다른 구글 계정으로 갈아타기 → 앞 계정 데이터가 섞이지 않는지.
- 5.5.9. 두 기기에서 동시에 다른 게임 진행 → 둘 다 살아남는지(5.2.8의 실환경 확인).
- 5.5.10. 구글 계정 설정에서 이 사이트 연결 해제 → 다음 방문 시 오류 없이 미로그인 상태로 돌아가는지.
- 5.5.11. 로그인 후 브라우저를 완전히 닫고 다시 들어오기 → 로그인이 유지되는지(4.4.3, 2026-07-31 추가). 폰 홈 화면 앱으로도 한 번 확인한다.

### 5.7. 기존 사용자 회귀 방지 (최우선)

이번 변경의 가장 큰 위험은 새 기능 실패가 아니라 **이미 놀던 사람의 데이터가 깨지는 것**이다.

- 5.7.1. 미로그인 사용자의 동작이 변경 전과 완전히 동일함을 5.3.1 + 5.4.3으로 확인.

- 5.7.3. **동기화 누락 키 0 검사**: 게임을 실제로 한 판씩 돌린 뒤 브라우저에 남은 저장 키 전부를 훑어, 업로드 문서에 담기지 않은 키가 있으면 실패로 본다. 제외 목록(4.6)에 명시된 것만 예외로 인정한다. 선언한 것과 실제 저장하는 것이 어긋나는 사고(글로벌 3.9 죽은 입력 대조)를 여기서 잡는다.
- 5.7.4. 되돌리기 경로: 문제가 생기면 `shared/storage.js`의 동기화 알림 한 줄만 꺼도 기존 동작으로 즉시 복귀하도록 설계한다. 되돌리기가 커밋 되돌리기 없이 가능해야 한다.

실제 로그인 확인 직후 사용자가 네 가지를 지시했다. 설계에 반영해 9.3에서 구현했다.

## 6. 구현 계획 (승인 후)

### 6.0. 원칙

6.0.1. **단계마다 그 자체로 배포 가능한 상태**로 끝낸다. 중간 단계가 반쯤 깨진 채 저장소에 남지 않는다. S1~S3은 사용자 눈에 보이는 변화가 0이므로 언제 멈춰도 안전하다.

6.0.2. **위험한 순서를 뒤로 민다.** 구글 연결(S5)이 마지막인 이유는, 그 앞 단계에서 데이터 로직이 이미 자동 검증으로 굳어 있어야 로그인 문제와 데이터 문제를 섞지 않고 진단할 수 있기 때문이다.

6.0.3. 단계별 1커밋. 커밋 메시지 scope는 `hub`.

### 6.1. 만들 파일

```
shared/cloud/
  merge.js      순수 로직 (window·fetch 등장 금지)
  local.js      기기 저장을 슬롯 단위로 읽고 쓰기 (gg.* + lotto_ 스캔)
  remote.js     드라이브 읽기·쓰기 + 테스트용 가짜 저장소
  auth.js       구글 로그인 + 테스트용 가짜 로그인
  sync.js       위 넷을 엮는 조립부
  ui.js         허브 버튼·계정 메뉴·충돌 대화상자
tests/
  cloud-merge.test.mjs
  cloud-sync.test.mjs
```

기존 파일 수정은 `shared/storage.js`(알림 1줄) / `games/lotto/src/data/storage.js`(함수 2개) / `index.html`(버튼 삽입) / `tests/smoke.mjs`(정적 검사 2개 추가) / `.claude/deploy.json`(테스트 명령 추가) 뿐이다.

### 6.2. 단계

| 단계 | 내용 | 사용자 눈에 보이는 변화 | 통과 조건 |
|---|---|---|---|
| S1 | `merge.js` + 1층 테스트 | 없음 | 5.2 전 13항목 통과 |
| S2 | `local.js` + `remote.js`(가짜) + `sync.js` + 2층 테스트 | 없음 | 5.3 전 9항목 통과 |
| S3 | `storage.js` / lotto 편입 | 없음(동기화 꺼짐 상태) | 게임 8종 실화면 콘솔 0 + 기존 테스트 전량 |
| S4 | `ui.js` + 허브 버튼 + 가짜 로그인 모드 | 버튼 보임(가짜 동작) | 5.4 실화면 4항목 |

### 6.3. 단계별 상세

#### S1. 순수 로직

공개 함수 초안. 전부 입력을 변형하지 않는 순수 함수다.

- `buildDocument(slots, { now, device })` → 업로드용 문서 객체
- `mergeDocuments(local, remote, { now, skewToleranceMs })` → `{ merged, apply: { toLocal, toRemote }, conflicts }`
- `validateDocument(doc)` → `{ ok, reason }`
- `estimateSize(doc)` → 바이트 수
- `checkUploadable(doc)` → `{ ok, reason, bytes }` (5.2.12의 "조용한 실패 0"을 순수 로직에서 보장)
- 상수 `SCHEMA = 1`, `MAX_BYTES`, `DEFAULT_SKEW_TOLERANCE_MS`, `EXCLUDED_KEYS`(4.6)

`conflicts`가 비어 있지 않으면 조립부가 4.7.3 대화상자를 띄운다. 즉 **"물어봐야 한다"는 판단도 순수 함수 안에서 내려지고 자동 검증된다.**

#### S2. 저장소와 조립부

- `local.js`: `readAllSlots()` / `writeSlot(namespace, data)`. `gg.*` 접두와 `lotto_` 접두 두 규칙을 알고 슬롯으로 환산한다.
- `remote.js`: `createDriveRemote({ getToken })`와 `createMemoryRemote(initial)`이 **같은 모양**(`load()` / `save(doc)`)을 갖는다. 이 동일 인터페이스가 2층 테스트의 전제다.
- `sync.js`: `createSync({ auth, remote, local, onStatus })` → `{ start, notifyChange, flushNow, pullNow, resolveConflicts }`. 디바운스(4.3.2)와 재시도가 여기 있다.

#### S3. 기존 저장 창구 편입 (되돌리기 지점)

- `shared/storage.js`의 `set()` / `remove()` 끝에 알림 1줄을 추가한다. 동기화 모듈이 없거나 꺼져 있으면 아무 일도 하지 않는다(느슨한 결합).
- lotto는 `read()` / `write()`에 같은 처리.
- **이 단계 완료 시점에도 사용자 동작은 변경 전과 같아야 한다.** 알림을 받는 쪽이 아직 없기 때문이다. 여기서 게임 8종 전수 회귀를 돌려, 이후 단계에서 문제가 나면 원인이 저장 창구가 아님을 확정한다.
- 되돌리기: 알림 1줄만 제거하면 원상복귀(5.7.4).

#### S4. 화면 (가짜 로그인으로 사람 없이 검증)

- `ui.js`가 4.7의 버튼·메뉴·대화상자를 그린다.
- 주소에 `?cloudmock=1`을 붙이면 가짜 로그인·가짜 저장소로 붙는다. 이 모드로 browser-shot 실화면 검증(5.4)을 사람 개입 없이 돌린다.
- 충돌 요약 문구(4.7.3.2)를 게임별로 등록한다. 등록 없는 게임은 시각만 표시.

#### S5. 진짜 구글 연결

- 구글 로그인 스크립트를 허브에 `<script>` 한 줄로 추가.
- `auth.js`가 `createAuth({ clientId })`를 노출하고, 등록번호는 `shared/cloud/config.js` 한 곳에만 둔다(비밀키 아님, 공개 저장소 게시 가능).
- **이 시점에 사용자께 8장 콘솔 작업을 요청한다.** 그전에는 요청하지 않는다 - 앞 단계에서 막히면 발급받은 값이 대기 상태로 방치되기 때문이다.

#### S6~S7

실계정 체크리스트(5.5)를 자비스가 순서대로 안내하고 결과를 이 문서 하단에 기록한다. 그 뒤 배포 편입(5.6)과 서비스워커 캐시 번호 상향.

### 6.4. 규모 추정 [추정]

S1~S4가 작업량의 대부분이고, 새로 쓰는 코드는 600~900줄 규모로 본다(테스트 포함). S5는 코드량은 적지만 실환경 변수가 많아 시간이 가장 예측하기 어렵다. 확정 수치가 아니라 추정이다.

### 9.3. S5 구글 연결 + 추가 요구 반영 - 완료 (2026-07-29)

실제 구글 계정 로그인 성공(사용자 실측). 경고 화면 없이 동의 후 "동기화됨"까지 도달했고, 실제 드라이브에 세이브 파일이 만들어졌다. 이어서 5.9의 네 가지 요구를 반영했다.

산출물 추가: `shared/cloud/auto.js`(게임 화면용 무화면 동기화). 수정: `auth.js`(진짜 구글 로그인), `remote.js`(진짜 드라이브 읽기·쓰기), `stamp.js`·`local.js`·`merge.js`·`sync.js`(기록 줄기·시작 시각), `ui.js`(라벨·X 버튼·시각 표시), 게임 8종 `index.html` 각 1줄, `service-worker.js`(캐시 번호 v195 + stamp.js 선캐시).

- 9.3.1. **저장 형식을 2로 올렸다.** 슬롯마다 기록 줄기(lineage)와 시작 시각(createdAt)을 갖는다. 줄기가 서로 다르면 시각이 최신이더라도 자동으로 덮지 않고 사용자에게 묻는다. 줄기 정보가 없는 옛 기록은 같은 줄기로 관대하게 취급해 기존 사용자를 보호한다(이미 드라이브에 올라간 형식 1 문서가 그 대상이다).
- 9.3.2. **게임 화면 동기화 분리.** 화면 요소는 허브에만 두고(7.4 유지), 게임 화면에는 눈에 보이지 않는 동기화만 붙였다. 진입 시 1회 내려받고, 저장은 2.5초로 모아 올리며, 화면을 벗어날 때 남은 변경을 밀어낸다. 로그인하지 않은 사용자에게는 구글 스크립트조차 불러오지 않는다. 게임 도중에는 어떤 것도 묻지 않고, 선택이 필요한 충돌은 올리지 않은 채 허브에서 처리한다.
- 9.3.3. **선택 화면에 시작·최종 저장 시각 표시.** "시작 7/20 21:50 · 최종 저장 7/29 21:45 (5분 전)" 형태로 양쪽 모두 보여준다.
- 9.3.4. **메뉴 정리.** 저장하기 (구글 드라이브) / 불러오기 (구글 드라이브) / 내보내기 (JSON 파일) / 로그아웃, 닫기는 오른쪽 위 X. 설명 문장은 두지 않는다(4.7.2).
- 9.3.5. **프로필 표시.** 이름을 받으려면 권한을 더 요구해야 해서 받지 않는다. 이름이 없을 때 물음표가 뜨던 것을 로그인 표시로 바꿨다.

검증: `cloud-merge` 25건, `cloud-sync` 18건, `smoke` 10건, lotto 324건, english-reading 전량 통과. 게임·앱 8종 실화면 재진입 콘솔 에러 0. 충돌 선택 화면과 계정 메뉴 실화면 확인.

미확인으로 남은 것: **두 기기 사이 실제 왕복은 아직 확인하지 않았다.** 배포 후 폰과 PC로 밟아야 한다(5.5.2 / 5.5.9).

### 9.4. 게임·앱마다 다른 저장 기준 - 완료 (2026-07-29, 사용자 지시)

사용자 지시: "게임마다, 앱마다 저장 기준이 달라야 할 것 같은데?" → "결국 저장파일 기준인건가". 기준을 두 층으로 나눠 `shared/cloud/policy.js` 한 곳에 모았다. 4.6의 제외 목록도 이 파일로 옮겨 단일 출처로 만들었다.

**1층: 항목(저장 키) 단위 - 무엇을 계정에 올리나.** 판단 기준은 "이 기기의 상태인가, 내 기록인가"다.

| 슬롯 | 올리지 않는 항목 | 이유 |
|---|---|---|
| tetris | `muted`, `lastMode` | 소리·마지막 고른 모드는 그 기기의 상태 |
| nonogram | `muted`, `mode` | 위와 같음 |
| flightshooting | `cheat`, `cheatCfg` | 개발용 |
| english-reading | `listScroll` | 폰의 스크롤 위치가 PC로 넘어오면 방해 |
| lotto | `draws`, `stats_*`, `s\d{3}_*` | 회차 캐시·파생값, 그리고 **1회성 데이터 정리 표식** |

`s090_cleared` 같은 정리 표식은 이번에 발견한 위험이다. 공유하면 새 기기에서 정리 작업이 건너뛰어져 데이터가 고쳐지지 않는다.

**1-2층: 덮어쓰지 않고 합쳐야 하는 항목.** 사용자 질문("영어 독해의 단어장, 문장 등도 다 공유되는거야?")에서 드러난 결함이다. 최고 기록은 하나만 남으면 되지만 모아나가는 것은 나중에 저장한 쪽이 통째로 이기면 다른 기기에서 모은 것이 사라진다. PC에서 단어 셋을 담고 폰에서 둘을 담으면 한쪽이 통째로 없어지는 상황이었다.

| 슬롯 | 항목 | 합치는 방식 |
|---|---|---|
| english-reading | `vocab` (단어장) | `wordKey`가 같으면 하나로 |
| english-reading | `savedSentences` (저장한 문장) | `key`가 같으면 하나로 |
| english-reading | `done` (완독 지문) | 중복 없이 합집합 |
| english-reading | `reads` (지문별 회독수) | 같은 지문은 큰 값 |
| lotto | `characters` (만든 캐릭터) | `id`가 같으면 하나로 |

여기 없는 값은 종전대로 최신 것을 쓴다. 읽던 자리(`progress`)나 단어장 앱의 학습 큐(`deck`)처럼 통째로 일관돼야 하는 값은 합치면 오히려 깨지므로 일부러 제외했다. 합쳐서 값이 달라지면 클라우드와 이 기기 **양쪽 모두에** 그 결과를 반영한다.

**1-3층: 이긴 쪽에 없어도 지우지 않는 항목.** 슬롯(게임) 하나가 통째로 최신 쪽을 따르므로, 이긴 기기에 없는 항목은 사라진다. 단어장 앱은 학습 세트마다 키가 따로라(`deck:1:set-a`, `deck:1:set-b`) 여기에 걸린다. PC에서 A세트, 폰에서 B세트를 공부하면 한쪽 세트가 통째로 없어진다. `deck:`으로 시작하는 키는 이긴 쪽에 없으면 진 쪽 것을 살린다.

**같은 세트를 양쪽에서 공부한 경우는 최신 쪽을 통째로 쓴다(의도).** 학습 상태는 남은 큐·라운드·되돌리기가 한 덩어리로 앞뒤가 맞아야 한다. 단어별 진행만 뽑아 합치려면 "외운 상태와 다시 외우기 중 어느 쪽이 우선인가"를 정해야 하는데, 그건 동기화가 아니라 학습 설계 결정이라 임의로 정하지 않았다. 한 기기씩 번갈아 쓰는 통상적인 사용에서는 시각 순서대로 정상 이어진다.

**2층: 게임 단위 - 얼마나 빨리 올리나.** 이어하기가 중요한 게임은 짧게, 저장이 잦은 앱은 길게 잡았다.

| 슬롯 | 대기 | 상한 | 시각 기록 간격 | 근거 |
|---|---|---|---|---|
| flightshooting / rushhour / sudoku / tetris | 1.2~1.5초 | 15초 | 0.5초 | 구역·판 단위 저장이라 드물다. 곧바로 올려도 부담 없고, 폰으로 바로 넘어갈 수 있어야 한다 |
| nonogram | 1.5초 | 15초 | 0.5초 | 위와 같음 |
| lotto | 2.5초 | 20초 | 1초 | 손으로 편집하는 작업이라 조금 모은다 |
| english-vocabulary | 4초 | 25초 | 1.5초 | 카드를 넘길 때마다 저장된다 |
| english-reading | 6초 | 30초 | 3초 | 목록 스크롤이 초당 수십 번 저장을 부른다 |

여러 게임이 함께 바뀌면 **가장 급한 쪽 기준**으로 올린다(느린 앱 때문에 급한 게임이 늦어지지 않게).

검증: `cloud-sync` 24건 / `cloud-merge` 25건 / `smoke` 10건 / lotto 324건 / english-reading 전량 통과. 게임·앱 8종 실화면 재진입 콘솔 에러 0. 새 테스트로 (1) 게임별 대기 시간이 실제로 다르게 적용되는지, (2) 여러 게임 동시 변경 시 급한 쪽을 따르는지, (3) 제외 항목이 올라가지 않으면서 이 기기에는 남는지, (4) 클라우드 데이터를 받아써도 제외 항목이 지워지지 않는지를 확인한다.

### 9.5. 충돌 오탐 수정 + 단어별 진행 병합 + 홈 라이트 테마 (2026-07-29)

**9.5.1. 사용자 신고: "이 기기에서 저장한 건데 왜 이 기기에서 선택하라고 하지?"** 실제 화면에서 lotto·flightshooting·nonogram 세 개가 한꺼번에 선택을 요구했다. 원인이 셋 겹쳤다.

- 같은 기기가 올린 기록인지 보지 않았다. 클라우드에 있는 것이 방금 이 기기가 올린 내 기록인데도 남의 기록처럼 물었다. → 슬롯에 어느 기기가 올렸는지 남기고, 내 기기가 올린 것이면 되묻지 않는다.
- 저장 시각이 없는 옛 기록(둘 다 0)을 "같은 시각에 저장됨"으로 오판했다. → 양쪽 다 시각을 모르면 묻지 않고 이 기기 것을 기준으로 삼는다. 화면의 "시작 기록 없음 · 최종 저장 기록 없음"이 그 상태였다.
- 시각이 없을 때 상대 시각이 빈 괄호 `()`로 남았다. → 값이 없으면 괄호를 만들지 않는다.

**9.5.2. 단어장 단어별 진행 병합 (사용자 결정: 더 많이 진행된 쪽).** 같은 학습 세트를 두 기기에서 공부한 경우, 단어마다 더 진행된 쪽을 남긴다. 한쪽에서 외웠으면 외운 것으로, 본 횟수·모른 횟수는 큰 값, 학습 시각은 최근 값. 남은 카드 순서와 회차는 섞지 않고 최신 쪽을 그대로 쓴다(섞으면 앞뒤가 안 맞는다). 큐에 남은 카드 중 이미 외운 것은 앱이 복원할 때 스스로 걸러낸다(`core/deck.js`의 기존 로직).

**9.5.3. 홈화면 라이트 테마 (사용자 지시).** `index.html`에서만 색 토큰을 덮어써 홈을 밝게 했다. 게임·앱 화면은 기존 다크 그대로다. 밝은 배경에서 대비를 잃는 값들을 함께 보정했다 - 모달 뒷막, 기본 버튼 글자색, 상태 배지(카드마다 다른 강조색을 물려받아 흐려지던 것을 고정 색으로), 클라우드 버튼 상태색, 브라우저 상단 색.

검증: `cloud-merge` 37건 / `cloud-sync` 24건 / `smoke` 10건 / lotto 324건 / english-reading 전량 통과. 홈 라이트 테마와 대화상자 실화면 확인, 게임 화면 다크 유지 + 콘솔 에러 0.

### 9.6. 데이터 유실 사고와 원칙 변경 (2026-07-29)

**사고.** 봉합 push가 곧 배포인 저장소 구조라 세션 봉합과 동시에 클라우드 저장이 실사용에 노출됐다. 사용자가 모바일에서 접속하자 그 기기에만 있던 저장이 사라졌고 복구하지 못했다. 설계 5.5(실계정 체크리스트 10항목)를 밟기 전에 배포된 것이 배경이다.

**원인 두 가지가 겹쳤다.**

- 9.6.1. 클라우드 저장을 붙이기 전부터 기기에 있던 데이터는 마지막 저장 시각이 없어 값이 0이다. 다른 기기가 올린 기록은 실제 시각을 가지므로 **시각 없는 쪽이 항상 졌다.**
- 9.6.2. 기기에 클라우드 내용을 쓸 때 **클라우드에 없는 항목을 지우도록** 만들었다. 위 판정과 만나 그 기기만의 기록이 통째로 대체됐다.

기존 방어(양쪽 다 시각 없을 때 기기 우선, 같은 기기가 올린 것은 되묻지 않음)는 이 경로를 덮지 못했다.

**원칙 변경: 동기화는 더하는 방향만 자동으로 한다. 지우는 방향과 많이 잃는 병합은 사람이 정한다.**

- 9.6.3. 기기에 있는 항목을 지우지 않는다(`local.writeSlot`에서 삭제 제거). 병합도 같다 - 진 쪽에만 있는 항목은 살린다. 대가로 한쪽에서 지운 항목이 되살아날 수 있으나, 유실보다 낫다는 판단이다.
- 9.6.4. 한쪽만 저장 시각을 모르면 자동 판정하지 않고 묻는다(`unknown-time`).
- 9.6.5. 겹치는 항목의 내용이 절반 이하로 줄어들면 묻는다(`big-loss`). 학습 상태처럼 겉이 항목 하나여도 안에 수십 개가 든 값을 놓치지 않도록 한 겹 안쪽까지 센다. 사용자 표현 그대로 "핸드폰 데이터가 훨씬 큰데 당연히 물어볼 줄 알았다"에 대응하는 규칙이다.
- 9.6.6. 어느 기기든 처음 동기화하기 직전 상태를 한 번 저장한다(`gg.__cloud.backup`, 이후 덮지 않음). 계정 메뉴 "처음 상태로 되돌리기"로 복구한다. 이 장치가 있었다면 이번 데이터를 살릴 수 있었다.

검증: 사고 재현 시나리오 3건을 자동 검사로 고정했다 - 시각 없는 데이터가 자동으로 밀리지 않는지, 많이 잃는 병합을 잡는지, 되돌릴 상태가 남는지. `cloud-merge` 37 PASS / `cloud-sync` 28 PASS / `smoke` 12 PASS / lotto 324 PASS.

**재활성.** 사용자 지시로 다시 켰다(등록번호 복원, 서비스워커 v198). 문제 발생 시 가장 빠른 차단은 `config.js`의 등록번호를 비우는 것이다 - 버튼과 배경 동기화가 모두 멈춘다.

### 9.7. 로그인이 자주 다시 물어보는 문제 - 수정 (2026-07-31)

**증상 보고.** 사용자: "구글 계정 로그인을 너무 빈번하게 물어본다. 다른 앱은 한 번 로그인하면 오래 유지된다." 콘솔 게시 상태는 이미 전환을 마친 상태여서(8.5 완료) 정책 쪽 원인은 배제됐다.

**원인 두 개가 우리 코드 쪽 결함이었다.**

- 9.7.1. `remote.js`가 드라이브의 "유효기간 지남" 응답을 받으면 **로그인 창을 띄우는 재발급**을 호출했다. 자동 저장은 게임 화면에서도 도는데(9.3) 그 통로가 같은 함수를 쓰므로, 4.4.4의 "게임 중간에 묻지 않는다" 규정이 코드 수준에서 무너져 있었다. 설계 문구는 맞았고 구현이 어긴 경우다.
- 9.7.2. 토큰을 세션 한정 보관에 두어(원래 4.4.3) 창을 닫으면 사라졌다. 재방문마다 조용한 재발급이 필요했고, 그 재발급은 구글 세션 쿠키에 의존하므로 홈 화면 실행·쿠키 제한 브라우저에서 자주 실패해 곧바로 로그인 요구로 보였다.

세 번째는 원인이 아니라 구조적 상한이다 - 브라우저 방식에는 갱신 토큰이 없어 접속 토큰 1시간을 늘릴 수 없다. 사용자가 비교한 다른 앱들은 그 갱신 토큰을 서버에 보관한다. 1.3.2(서버 운영 금지)를 유지하는 동안 이 상한은 남는다.

**고친 것 세 가지** (사용자 승인 2026-07-31 "모두 고쳐줘").

- 9.7.3. 거절 응답을 받으면 창을 띄우지 않는다(4.4.5 신설). 갖고 있던 토큰을 버리고 조용한 재발급만 한 번 시도하고, 실패하면 동기화만 멈춘다. 토큰을 버리는 단계가 없으면 재발급이 같은 죽은 토큰을 돌려주므로 재시도가 무의미해진다 - `auth.invalidateToken()`을 신설해 `remote`에 주입했다.
- 9.7.4. 토큰 보관을 창 닫아도 남는 곳으로 옮겼다(4.4.3 개정). 이전 위치에 남은 값은 첫 접근 시 이관해 이미 로그인해 둔 사용자가 다시 로그인하지 않게 했다. 여러 페이지가 열려 있으면 한쪽이 갱신한 토큰을 다른 쪽이 이어 쓴다.
- 9.7.5. 만료 5분 전에 미리 조용히 갱신한다(4.4.2 보강). 만료 뒤에 갱신하면 그 순간이 사용자 조작 중일 수 있다. **(2026-08-01 폐기 - 이 처방의 전제가 틀렸다. 9.8 참조.)**

**검증.** 신규 `tests/cloud-auth.test.mjs` **13 PASS**(보관 위치 6건 / 선제 갱신 3건 / 창 금지 4건). 창이 뜨는 호출을 가짜 구글 라이브러리로 가로채 세는 방식이라, 규정 위반이 코드로 돌아오면 검사에서 잡힌다. `smoke.mjs`에 정적 검사 2건을 더해(`remote.js`·`auto.js`에 창을 띄우는 재발급 문자열 금지) 9.7.1 재발을 막았다. 회귀: `cloud-merge` 37 PASS / `cloud-sync` 28 PASS / `smoke` 14 PASS / lotto 324 PASS / english-reading 통과. 실화면: 허브·게임 진입 시 스크립트 오류 0(잡힌 404는 `favicon.ico` 하나로 이 변경과 무관한 기존 상태).

**남은 확인은 사람 몫이다.** 실제 로그인 유지 개선은 실계정에서만 측정된다(5.5 체크리스트 성격). 확인 방법: 로그인 후 브라우저를 완전히 닫고 다시 들어와 우상단 버튼이 "저장"이 아니라 동기화 상태로 보이는지, 한 시간 이상 열어둔 뒤 게임을 저장할 때 로그인 창이 뜨지 않는지.

### 9.8. 팝업 2번 + 1시간마다 풀림 (2026-08-01 사용자 신고 → 주소 이동 갱신 도입)

사용자 신고 셋. 로그인 팝업이 2번씩 뜬다 / 팝업을 막아 두면 아예 뜨지 않는다 / 다른 사이트는 로그인이 오래 유지되는데 여기는 1시간마다 풀리는 것 같다.

**뿌리는 9.7의 처방이 깔고 있던 잘못된 전제였다.** 구글 로그인 부품에 요청할 때 prompt를 비우면 "창 없이 조용히" 재발급된다고 보고 4.4.2를 그렇게 규정했는데, 그 부품은 실제로는 그 경우에도 팝업 창을 열고 즉시 닫는다. 검사 코드까지 그 전제를 그대로 옮겨 적어("prompt가 '' 인 호출은 창을 띄우지 않는 조용한 재발급") 13건이 모두 통과하고 있었다 - 검사가 구현을 검증한 것이 아니라 같은 오해를 두 번 쓴 상태였다. 여기서 셋이 파생됐다.

- 9.8.1. 만료 5분 전 예약 갱신이 팝업을 열었다. 그 시점은 사용자 조작이 없는 순간이라 브라우저가 팝업을 차단한다 → 갱신 실패 → 1시간마다 로그인이 풀린 것으로 보였다. 차단하지 않은 사용자에게는 창이 번쩍였다.
- 9.8.2. 진행 중인 요청을 공유하지 않아, 같은 순간에 두 곳이 출입증을 달라고 하면 창이 두 개 열렸다. 실패한 조용한 갱신을 억제하는 장치도 없어 화면을 나갈 때·저장할 때마다 다시 시도했다.
- 9.8.3. 유효기간이 끝나 동기화가 멈춘 상태에서 허브 버튼에는 "다시 로그인"이라고 적혀 있는데, 누르면 로그인 창이 아니라 계정 메뉴가 열렸다(라벨과 동작 불일치).

**고친 것 넷** (사용자 결정 2026-08-01 "1순위로 진행").

- 9.8.4. 조용한 경로에서 창을 여는 호출을 전부 없앴다(4.4.6.3). 창은 사용자가 버튼을 누를 때만 뜬다.
- 9.8.5. 만료된 로그인은 허브 진입 때 같은 창을 구글에 다녀오게 해서 되살린다(4.4.6.1/4.4.6.2). 팝업이 아니라 주소 이동이므로 차단 설정과 무관하고, 구글 자체 로그인 세션이 살아 있으면 화면이 한 번 깜빡이고 돌아온다. 되돌이 방지는 세션당 1회 + 실패 후 30분 억제의 이중 장치.
- 9.8.6. 같은 순간의 중복 요청을 하나로 묶었다(4.4.6.4). 요청이 끝나면 잠금이 풀린다.
- 9.8.7. "다시 로그인" 라벨을 누르면 로그인 창이 뜨고 성공 시 곧바로 내려받는다(9.8.3 해소).

**콘솔 등록이 선행 조건이다.** 주소 이동 방식은 구글 콘솔의 "승인된 리디렉션 URI"에 배포 주소가 등록돼 있어야 한다. 등록 없이 켜면 사용자가 400 오류 화면에 갇히므로 `config.js`에 끄고 켜는 스위치를 두었다. 확인 절차는 그 주소로 직접 요청을 보내 어디로 돌아오는지 보는 것이다(자비스가 실행 가능) - 미등록이면 `redirect_uri_mismatch` 400 화면, 등록됐으면 허브로 되돌아온다. 2026-08-01 두 번 실측했다. 1차 미등록 확인 → 사용자가 콘솔 등록 → 2차에서 허브 복귀 확인 후 스위치를 켜고 배포했다. 문제가 생기면 스위치를 되돌리는 것이 가장 빠른 차단이고, 팝업 중복·반복 시도 수정(9.8.4/9.8.6/9.8.7)은 스위치와 무관하게 남는다.

**검증.** `tests/cloud-auth.test.mjs`를 새 전제로 다시 써서 **30 PASS**(보관 위치 5건 / 창 금지 5건 / 이동 조건 9건 / 결과 받기 6건 / 거절 대응 4건 등). 잘못된 전제를 옮겨 적었던 옛 검사 문구도 함께 걷어냈다. 회귀: `cloud-merge` 39 / `cloud-sync` 29 / `frame` 23 / `fullscreen` 16 / `smoke` 29 전량 PASS. 실화면: 허브·게임 진입 스크립트 오류 0(404는 `favicon.ico` 하나로 기존 상태), 가짜 모드에서 로그인 → 계정 메뉴 흐름 회귀 없음. 실계정에서만 확인되는 항목(창이 한 개만 뜨는지, 1시간 후 유지되는지)은 5.5.5/5.5.7로 넘긴다.
