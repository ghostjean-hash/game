# 걸음 A - 저장 규격과 러시아워 이관 (설계)

작성: 2026-09-06 / 대상 일감: T-115 / 기준 문서: 기획서 Ⅲ권 4.1 · 8장 걸음 A · 9.1

## 1. 이 설계가 하는 것과 안 하는 것

1.1. 하는 것은 둘이다. **저장 칸 여덟을 실제 키 구조로 확정**하고, **러시아워의 기존 저장을 그 위로 옮긴다.**

1.2. 하지 않는 것은 화면과 로직이다. 진행 맵·상점·꾸미기 화면은 그대로 두고, 러시아워의 게임 규칙도 한 줄도 건드리지 않는다. 걸음 A는 데이터가 놓이는 자리만 바꾼다.

1.3. **다른 게임 여섯은 이 판에서 아무 영향도 받지 않는다.** 지금 쓰고 있는 저장 함수(기록·이어서 하기·소리)를 그대로 두고 새 것을 옆에 더한다. 기획서 2.2의 "기본값은 항상 없음 쪽"이 여기 그대로 적용된다 - 새 칸을 쓰겠다고 선언하지 않은 게임에는 새 칸이 생기지 않는다.

1.4. 위험 등급은 높음이다. 영속 데이터를 다루고 사용자 진행을 잃을 수 있으므로 **구현도 오퍼스다.** 소넷으로 내리지 않는다.

## 2. 저장 칸 여덟의 실제 모양

2.1. 칸 하나가 키 하나다. 게임 `rushhour`이면 `gg.rushhour.<칸이름>`에 담긴다. 지금 쓰는 네임스페이스 규칙(`shared/storage.js`)을 그대로 쓰므로 클라우드 신호도 그대로 간다.

2.2. 각 칸의 구조.

```
progress   { active, modes: { <갈래>: { best, current, extra, stages: { <판id>: {…} } } } }
wallet     { <재화이름>: 숫자 }
owned      { <종류>: [ "품목id", … ] }
equipped   { <종류>: "품목id" }
resume     { at, detail, data }          (기존 형식 그대로)
muted      true | false                  (기존 형식 그대로)
prefs      { <항목이름>: 값 }
game       { … }                          게임 자유. 플랫폼은 안을 보지 않는다
schema     숫자                            이관 판별용
```

2.3. `progress` 안쪽을 더 푼다.

| 자리 | 담는 것 | 없어도 되는가 |
|---|---|---|
| `active` | 마지막으로 고른 갈래 이름 | 갈래가 하나면 없음 |
| `modes.<갈래>.stages.<판id>` | `{ cleared, stars, best:{value,at}, at }` | 판 개념이 없으면 빈 객체 |
| `modes.<갈래>.best` | 갈래 전체의 최고 기록 `{value,at}` | 판별 기록만 쓰면 없음 |
| `modes.<갈래>.current` | 그 갈래에서 마지막으로 열었던 판 | 없어도 됨 |
| `modes.<갈래>.extra` | 그 갈래에 딸린 **게임 고유 값**. 플랫폼은 안 본다 | 없어도 됨 |

판 하나가 담는 것은 `{ cleared, stars, best:{value,at} }`이다. 처음에는 판 단위 시각(`at`)도 함께 적었는데 옛 데이터에 그 값이 없고 러시아워가 판별 시각을 화면에 쓰지도 않아 넣지 않았다(구현 중 정정, 1회차 검사 지적). 필요한 게임이 나오면 그때 더한다.

갈래가 없는 게임은 갈래 이름을 `default` 하나로 쓴다. 갈래라는 말을 게임이 몰라도 되게 하려는 것이다.

2.4. **최고 기록은 `{value, at}` 하나로 모은다.** 지금 세 형식으로 갈린 것을 이 형식으로 통일한다. 값이 클수록 좋은지 작을수록 좋은지는 게임이 저장할 때 한 번 알려 준다(기존 `saveBest`와 같은 방식).

2.5. `game` 칸은 규격이 뜻을 정하지 않는 유일한 자리다. 위 일곱 칸 어디에도 안 맞는 값이 여기 온다. 플랫폼은 통째로 보관만 하고 열어 보지 않는다.

## 3. 새 부품 - 저장 그릇 확장

3.1. 파일은 새로 만들지 않고 **`shared/frame/save.js`를 확장한다.** 저장을 맡는 부품이 이미 그 자리에 있고, 새 파일을 만들면 게임이 저장을 두 군데서 가져오게 된다.

3.2. `createSave(gameId)`가 받는 것을 하나 늘린다.

```
createSave(gameId, { schema, migrate })
```

- `schema` - 이 게임이 기대하는 저장 판 번호. 넘기지 않으면 이관을 아예 시도하지 않는다(기존 게임 여섯이 여기 해당한다).
- `migrate` - 옛 저장을 새 칸으로 옮기는 함수. 게임이 넘긴다. 옛 구조는 게임마다 다르므로 플랫폼이 대신 알 수 없다.

3.3. 늘어나는 함수. 기존 함수(`saveResume`·`readResume`·`hasResume`·`clearResume`·`saveBest`·`readBest`·`readMuted`·`saveMuted`·`get`·`set`·`remove`)는 **이름도 동작도 그대로 둔다.**

| 새 함수 | 하는 일 |
|---|---|
| `readProgress()` | `progress` 칸을 읽는다. 없으면 빈 뼈대를 돌려준다 |
| `writeProgress(p)` | `progress` 칸을 통째로 쓴다 |
| `readWallet()` / `writeWallet(w)` | 지갑 |
| `readOwned()` / `writeOwned(o)` | 산 것 |
| `readEquipped()` / `writeEquipped(e)` | 쓰는 것 |
| `readPrefs()` / `writePrefs(p)` | 환경설정 값 |
| `readGame()` / `writeGame(g)` | 게임 자유 칸 |
| `readSchema()` | 지금 저장이 몇 판인지 |

3.4. 값을 읽을 때 **모양이 깨져 있으면 빈 뼈대로 되돌린다.** 저장이 사람 손이나 옛 버전 때문에 이상한 모양일 수 있고, 그때 게임이 죽는 것보다 처음부터 시작하는 편이 낫다. 단 이 경우에도 원본은 지우지 않는다.

## 4. 이관 - 언제 어떻게 도는가

4.1. `createSave`가 만들어질 때 딱 한 번 판정한다.

```
1. schema를 넘기지 않았으면    → 아무 일도 하지 않는다 (기존 게임 여섯)
2. 저장이 비어 있으면          → schema만 적어 둔다 (새 사람)
3. 저장의 schema가 목표와 같으면 → 아무 일도 하지 않는다 (이미 옮긴 사람)
4. 그 밖                       → 원본을 백업하고 migrate를 부른다
```

4.2. **원본 백업이 먼저다.** `migrate`를 부르기 전에 그 게임 네임스페이스의 모든 키를 통째로 복사해 `__backup` 칸에 남긴다. 담는 것은 `{ at, schema, data:{키:값} }`이다. 이 백업은 지우지 않는다 - 이관이 잘못됐을 때 되돌릴 유일한 길이다.

4.3. `migrate`는 **순수 함수로 만든다.** 옛 저장 전체를 담은 객체 하나를 받아 새 칸들을 담은 객체 하나를 돌려준다. 저장을 직접 만지지 않는다. 이렇게 해야 화면 없이 검사할 수 있다(6.1).

```
migrate(old) -> { progress, wallet, owned, equipped, prefs, game }
```

4.4. 플랫폼은 돌아온 칸들을 저장하고 `schema`를 목표 번호로 올린다. **여기까지가 한 덩어리다.** 중간에 실패하면 schema를 올리지 않아 다음에 다시 시도한다.

4.5. 이관이 두 번 도는 것을 막는 것은 `schema` 값 하나다. 백업 존재 여부로 판정하지 않는다 - 백업이 지워져도 이미 옮긴 저장을 다시 옮기면 안 되기 때문이다.

4.5.1. **다만 판 번호만으로는 부족하다**(구현 중 보강, 1회차 검사가 재현해 낸 경로). 계정 저장은 기기 사이를 오간다. 한 기기가 새 판으로 올라간 뒤에도 다른 기기가 아직 옛 빌드면 그 기기가 옛 모양 진행을 계정에 올리고, 그것이 내려오면 **판 번호는 그대로인데 내용만 옛 모양**이 된다. 그 상태로는 깬 판·별·최고 기록이 화면에서 통째로 비어 보인다.

그래서 게임이 `verify(저장전부)`를 하나 더 넘긴다. 판 번호가 맞아도 이것이 false면 다시 옮긴다. 넘기지 않은 게임은 종전대로 번호만 본다(기본값은 없음 쪽, 1.3).

4.5.2. **다시 옮길 때 진행 밖 값을 잃지 않는다.** 처음에는 "옛 저장에 그 값이 없으니 지금 값을 받침으로 쓰면 된다"고 적었는데 **그 전제가 틀렸다**(2회차 검사가 재현). 옛 모양 진행 덩어리 안에는 골드·산 것·쓰는 것이 함께 들어 있다. 그래서 받침만으로는 옛 기기의 값이 이겨, 다시 옮길 때마다 그 사이 번 골드와 산 물건이 되돌아간다. 백업은 이미 있어 덮지 않으므로 되돌릴 곳도 없다.

그래서 **어느 쪽이 이기는지를 상황에 따라 가른다.** 플랫폼이 옮기기를 부를 때 첫 옮기기인지 다시 옮기기인지 함께 알려 준다.

| 상황 | 진행 | 지갑·산 것·쓰는 것·게임 칸 |
|---|---|---|
| 첫 옮기기 | 옛 값 | **옛 값이 이긴다**(새 칸이 아직 비어 있다) |
| 다시 옮기기 | 내려온 옛 값 | **지금 값이 이긴다**(이 기기가 그 뒤에 번 것) |

4.5.3. 판 번호를 올릴 때의 초기화는 다른 장치가 막는다 - 갈래가 이미 새 모양이면 그대로 이어받는다.

4.6. **백업 칸은 계정으로 올리지 않는다.** 이 기기에서 옮기기 전 상태를 남기는 것이 목적이라 다른 기기로 갈 이유가 없고, 저장을 통째로 복사한 것이라 크기도 크다. 계정 저장이 제외할 키를 적어 두는 자리(`shared/cloud/policy.js`)에 이 칸을 넣는다.

## 5. 러시아워 - 무엇이 어디로 가는가

5.1. 지금 러시아워는 `progress` 키 하나에 전부를 담고 있다. 아래 표대로 흩어 담는다. 목표 판 번호는 `2`다(지금은 번호 자체가 없어 `readSchema()`가 `0`을 돌려준다).

| 지금 자리 | 가는 자리 | 비고 |
|---|---|---|
| `gold` | `wallet.gold` | |
| `ownedThemes[]` | `owned.theme` | |
| `ownedAccessories[]` | `owned.accessory` | |
| `equippedTheme` | `equipped.theme` | |
| `equippedAccessory` | `equipped.accessory` | |
| `ponyStyle` | `equipped.style` | 꾸미기의 캐릭터 고르기 |
| `blockOpts` | `game.blockOpts` | 켜고 끄는 값이라 상점 모델에 안 맞음. 게임 칸이 제자리다 |
| `activeMode` | `progress.active` | |
| `modes.<갈래>.cleared[]` | `progress.modes.<갈래>.stages.<판id>.cleared` | 목록을 판별 항목으로 편다 |
| `modes.<갈래>.stars.<판id>` | 같은 자리의 `.stars` | |
| `modes.<갈래>.best.<판id>` | 같은 자리의 `.best.value` | `at`은 옛 데이터에 없으므로 `null` |
| `modes.<갈래>.current` | `progress.modes.<갈래>.current` | |
| `modes.<갈래>.combo` · `bestCombo` | `progress.modes.<갈래>.extra` | 연속 클리어는 러시아워 고유 규칙 |
| `muted` | **버린다** | 소리 설정은 공용 `muted` 칸에 이미 따로 있다. 두 곳에 있던 것을 하나로 모으는 자리다 |
| 옛 단일 구조(최상위 `cleared`/`best`/`stars` + 별도 `current` 키) | 오리지널 갈래로 | 지금 코드가 이미 하고 있는 하위호환을 그대로 옮긴다 |

5.2. **소리 설정을 버리는 것이 유일하게 값을 잃는 자리다.** 공용 칸에 같은 값이 이미 있고 실제로 동작하는 것도 그쪽이라 잃는 것이 없다. 다만 공용 칸이 비어 있고 옛 값이 켜져 있는 경우가 있을 수 있으므로, **공용 칸이 비어 있을 때만** 옛 값을 옮겨 준다.

## 6. 러시아워 코드는 얼마나 바뀌는가

6.1. **게임 로직은 한 줄도 바꾸지 않는다.** `main.js`는 지금 `progress()`가 돌려주는 모양(하나의 큰 객체)을 700줄에 걸쳐 읽고 있다. 그 모양을 그대로 유지하는 얇은 어댑터를 두 함수 안에만 넣는다.

```
progress()      새 칸 여럿을 읽어 → 옛 모양 객체로 조립해 돌려준다 (메모리 캐시는 그대로)
saveProgress(p) 옛 모양 객체를 받아 → 새 칸 여럿으로 흩어 저장한다
```

6.1.1. **변환 규칙 자체는 `games/rushhour/src/data/save-shape.js`에 순수 함수로 둔다**(구현 중 정정, 2026-09-06). 처음에는 `main.js` 안에 두려 했는데, 그러면 옮기기만 검사할 수 있고 **왕복이 값을 잃지 않는지는 검사할 길이 없다.** 이 판에서 가장 큰 위험이 값 손실인데 그 절반을 화면 검사에만 맡기게 된다. 그래서 옮기기(`migrateToPlatform`)와 변환기(`assembleShape`·`scatterShape`) 셋을 한 파일에 순수 함수로 모았다. `main.js`는 저장을 읽어 넘기고 돌려받은 것을 쓰기만 한다.

6.2. 그래서 실제로 바뀌는 자리는 `main.js`에서 **세 함수와 그 언저리뿐**이다 - `migrateProgress`(파일 밖으로 나감) · `progress()` · `saveProgress()`. 나머지 호출자 일곱 곳은 손대지 않는다.

6.3. 어댑터는 **임시 구조물이고 그 사실을 코드에 적어 둔다.** 걸음 B에서 진행이 플랫폼으로 가면 조립하던 절반이 사라지고, 걸음 C에서 지갑·상점이 가면 나머지가 사라진다. 걸음 A에서 700줄을 한꺼번에 고치면 무엇이 깨졌는지 가릴 수 없어 일부러 나눈 것이다.

## 7. 무엇으로 확인하는가

7.1. **기계 검사** - `tests/save.test.mjs`를 새로 만든다. `migrate`가 순수 함수라 화면 없이 돌릴 수 있다. 확인할 다섯.

1. 실제 저장 모양을 그대로 넣었을 때 골드·산 것·쓰는 것·갈래별 진행이 값 하나까지 같은가
2. 저장이 아예 없을 때 빈 뼈대가 나오고 오류가 없는가
3. 옛 단일 구조(갈래가 없던 시절)를 넣으면 오리지널 갈래로 들어가는가
4. 이미 옮긴 저장을 다시 열면 이관이 돌지 않는가
5. 모양이 깨진 저장을 넣어도 죽지 않는가
6. **조립했다 다시 흩어 담아도 값이 하나도 바뀌지 않는가**(6.1.1로 검사할 수 있게 된 자리)
7. 백업이 남는가, 이미 있으면 덮지 않는가, 판 번호를 안 넘긴 게임에는 아무 일도 없는가
8. 옛 모양이 되돌아오면 알아보고 다시 옮기는가, 그때 그 사이 번 골드와 산 물건을 지키는가(4.5.1·4.5.2)
9. 판 번호를 올려도 이미 새 모양인 진행과 지갑이 초기화되지 않는가(4.5.3)
10. 저장할 때 게임 칸의 다른 항목을 지운 채로 덮지 않는가

7.2. **기존 검사 전량** - `tests/frame.test.mjs` 외 루트 검사가 그대로 통과해야 한다. 기존 저장 함수를 건드리지 않았다는 증거다.

7.3. **실화면** - 러시아워를 실제 브라우저로 연다. 이관 전 화면을 먼저 찍어 두고 이관 뒤와 대조한다.

- 시작 화면 기록 줄의 **모은 별·골드·갈래별 클리어 수**가 이관 전과 같은가 (이 한 줄이 이관 결과를 그대로 비추는 자리다)
- 진행 맵에서 깬 판의 별이 전과 같은가
- 상점에서 산 것이 그대로 있고 쓰는 것이 유지되는가
- 꾸미기에서 고른 캐릭터·배경·테두리가 그대로인가
- 판 하나를 새로 깨면 골드가 늘고 그 값이 나갔다 들어와도 남는가
- 저장을 지운 새 사람으로 열어도 정상인가

7.4. **되돌리는 길** - 이관이 잘못됐다고 판단되면 `__backup` 칸의 값을 원래 키로 되돌리고 `schema`를 지우면 이관 전 상태가 된다. 이 절차를 설계서에 적어 두는 것으로 충분하며, 되돌리는 화면을 만들지 않는다.

## 8. 하지 말 것

8.1. 다른 게임 여섯의 저장을 건드리지 않는다. `schema`를 넘기지 않은 게임에는 아무 일도 일어나지 않아야 한다.

8.2. 기존 저장 함수의 이름·동작·저장 키를 바꾸지 않는다(`saveBest`·`readBest`·`resume`·`muted`).

8.3. 러시아워의 게임 규칙·보상 값·난이도·화면을 바꾸지 않는다. 옮기는 판이지 다듬는 판이 아니다.

8.4. 어댑터 밖의 `main.js` 코드를 고치지 않는다. 눈에 띄는 개선거리가 보여도 걸음 B·C의 몫이다.

8.5. 진행 맵·상점·꾸미기 화면을 공용으로 옮기지 않는다(걸음 B·C).

8.6. 백업 칸을 지우거나 덮어쓰지 않는다.

8.7. 새 기능을 만들지 않는다. 도감·업적·순위표는 규격에 자리만 있고 이번 범위가 아니다.

## 9. 모델 배정

영속 데이터 + 사용자 자료를 잃을 수 있는 변경 + 공용 인터페이스 변경 셋에 모두 걸린다. **구현도 오퍼스다.** 소넷으로 내리지 않는다.
